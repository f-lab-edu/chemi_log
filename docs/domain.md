# Domain

케미로그의 비즈니스 개념과 불변 규칙.

**이 문서의 기준은 `database/init/01-schema.sql` 과 PRD 입니다.**
백엔드 도메인 코드는 옛 스키마를 기준으로 작성돼 있어 폐기했습니다. 이 저장소에 없습니다.
다시 짜야 하는 범위는 `docs/architecture.md` 머리말에 있습니다.

2026-08-27 ERD 재설계로 방 상태와 제출 상태가 저장 컬럼에서 파생값으로 바뀌었고,
질문 스냅샷이 값 복사에서 참조로 바뀌었습니다. 근거는 `docs/database.md` 에 있습니다.

서비스 개요: 여러 명이 같은 질문에 각자 답하고, 답변을 비교해 서로의 케미 점수와
모임 안 관계 순위를 확인합니다 (`README.md`).

## 개념

### Question: 원본 질문 (Master)

서비스가 보유한 질문 Pool. 방과 무관하게 존재합니다.

| 속성 | 값 |
| --- | --- |
| `category` | `CONVERSATION` / `TRAVEL` / `LIFESTYLE` / `SPENDING` |
| `content` | 질문 본문 |
| `option_a`, `option_b` | 2지선다 보기 |
| `active` | 방 생성 시 후보로 쓸지 여부 |

불변 규칙:

- 한 카테고리 안에서 `content` 는 유일합니다: `UNIQUE (category, content)`.
  시드를 두 번 적용하면 여기서 멈춥니다. 없으면 같은 문항이 새 `id` 로 들어가
  한 방에 똑같은 질문이 두 번 나올 수 있습니다 (`docs/database.md`)

현재 시드는 카테고리별 30문항, 총 120문항입니다 (`database/init/02-seed.sql`).
카테고리마다 성향 6개를 정해 5문항씩 배분했습니다. **질문을 추가할 때 그 배분을 지켜야 합니다.**
카테고리 점수를 3문항으로 계산하므로, 30개가 모두 같은 성향을 재면 어느 3개를 뽑아도
결과가 같아져 점수가 0점 아니면 100점으로 몰립니다. 근거는 시드 파일 머리말에 있습니다.

**한 번 넣은 질문의 `category`, `content`, `option_a`, `option_b` 는 고치지 않습니다.**
문구를 바꾸려면 새 행을 넣고 옛 행을 `active = FALSE` 로 내립니다.
이 전제 위에서 `room_question` 이 값을 복사하지 않고 참조만 합니다.
DB 는 이 전제를 강제하지 않습니다. 근거와 검토 과정은 `docs/database.md` 의
"질문은 불변입니다" 참고. **그 절은 임의 수정 금지 대상입니다.**

`active = FALSE` 로 내려도 행은 남으므로 그 질문을 쓰던 방은 그대로 보입니다.

### Room: 케미방

한 번의 케미 측정 단위. 공유 코드로 접근합니다.
**방이 저장하는 고유한 사실은 공유 코드뿐입니다.** 상태 컬럼이 없습니다.

| 상태 | 의미 | 어떻게 판정하나 |
| --- | --- | --- |
| `HOST_ANSWERING` | 방이 만들어졌고 방장이 아직 답변 중. 다른 사람은 참여할 수 없습니다 | 방장의 `submitted_at IS NULL` |
| `OPEN` | 방장이 답변을 제출해 참여자를 받는 상태 | 방장의 `submitted_at IS NOT NULL` |

**저장하지 않을 뿐 개념이 사라진 것은 아닙니다.** API 응답에는 위 두 값을 그대로 담습니다
(PRD 7장, 20장). 프론트엔드는 응답만 보므로 저장 방식의 차이를 모릅니다.

**정상 상태 전이는 하나뿐입니다.**

```text
HOST_ANSWERING  →  OPEN
```

역방향 전이, 그 외 상태는 현재 설계에 없습니다. 필요해 보여도 임의로 추가하지 마십시오.

`OPEN` 으로의 전이는 **방장이 답변을 제출한 뒤에만** 일어납니다 (PRD 5장).
**전이를 위해 갱신하는 컬럼은 방장의 `participant.submitted_at` 하나입니다.**
옛 설계는 `room.status` 와 `participant.answer_status` 를 함께 갱신해야 했고
두 테이블에 걸친 조건이라 DB CHECK 로 묶지도 못했습니다. 한쪽만 반영되면 방장은 답을 냈는데
친구는 "방장이 준비 중" 화면에서 막혔습니다. 지금은 값이 한 곳에만 있어 어긋날 방법이 없습니다.

### RoomQuestion: 방에 고정된 질문 12개

**질문 값을 복사하지 않습니다.** `question` 을 참조만 합니다 (`room_id`, `question_id`).

PRD 8장은 이미 만들어진 방의 질문과 결과가 바뀌지 않을 것을 요구합니다.
참조만 해도 그 요구가 지켜지는 이유는 **원본이 바뀌지 않기 때문**입니다.
위 Question 절의 불변 전제가 이 설계의 근거입니다.

불변 규칙:

- 한 방에 같은 질문이 두 번 들어가지 않습니다: `UNIQUE (room_id, question_id)`
- 방 하나는 질문 12개를 가집니다. **개수 12는 DB로 보장되지 않습니다.**
  방 생성 트랜잭션과 테스트에서 확인해야 합니다
- 표시 순서 컬럼이 없습니다. 순서는 `id` 오름차순입니다.
  **조회할 때 `ORDER BY rq.id` 를 빠뜨리면 순서가 보장되지 않습니다**
- 방의 질문을 조회할 때 `question` 과 **조인해도 됩니다.**
  질문이 불변이라 옛 방에 새 문구가 붙지 않습니다

마지막 항목은 옛 설계와 정반대입니다. 옛 설계는 값을 복사해 두고 "조인하지 마라" 는 규칙으로
스냅샷을 지켰고, 그 규칙은 DB 로 강제할 수 없었습니다. 되돌리지 마십시오.

### Participant: 참여자

방에 들어온 사람. 방장도 참여자입니다. `is_host = TRUE` 인 행이 방장입니다.

| 상태 | 의미 | 어떻게 판정하나 |
| --- | --- | --- |
| `ANSWERING` | 답변 작성 중 | `submitted_at IS NULL` |
| `SUBMITTED` | 답변 제출 완료 | `submitted_at IS NOT NULL` |

Room 상태와 마찬가지로 저장하지 않고 API 응답에는 그대로 담습니다.

불변 규칙:

- 한 방 안에서 닉네임은 중복될 수 없습니다: `UNIQUE (room_id, nickname_key)`
- 방마다 방장은 한 명입니다. **DB 가 강제하지 않습니다.** `is_host = TRUE` 를 만드는 곳이
  방 생성 한 군데뿐이고, 링크로 들어오는 참여자는 항상 `FALSE` 로 만들어집니다
- `submitted_at` 은 `NOW(6)` 로 채웁니다. 앱이 `LocalDateTime.now()` 로 채우면
  `created_at` 과 기준이 달라집니다. `DATETIME` 은 시간대를 담지 않으므로 JVM 이 UTC 인
  컨테이너에서는 9시간 이르게 저장되고 DB 는 아무 오류도 내지 않습니다

닉네임은 표시용 `nickname` 과 중복 검사용 `nickname_key` 로 나뉩니다.
정규화(trim, 연속 공백 축소, NFC, 공백 전부 제거, `toLowerCase(Locale.ROOT)`)는
**전부 애플리케이션에서** 수행합니다.
`Locale` 인자를 빼면 터키어 로케일에서 `I` 가 `ı` 로 바뀌어 서버마다 결과가 달라집니다.

**공백 전부 제거는 `nickname_key` 에만 적용합니다.** `nickname` 에는 내부 공백이 남습니다.
PRD 7장이 공백 제거를 중복 판정에만 적용하도록 나눠 뒀습니다. `지 은` 으로 입력한 사람은
화면에 `지 은` 으로 보이고, 중복 판정에서만 `지은` 과 같은 사람으로 취급됩니다.
사전 중복 조회에서 이 단계를 빠뜨리면 `min su` 와 `minsu` 를 다른 이름으로 통과시킨 뒤
INSERT 에서 `UNIQUE (room_id, nickname_key)` 위반이 나서 409 대신 500 이 나갑니다.

**프론트엔드가 trim 과 연속 공백 축소를 이미 하지만 서버는 그것을 믿지 않습니다.**
프론트의 정규화는 입력 결과를 사용자에게 미리 보여주기 위한 것입니다.
`POST /api/rooms` 는 브라우저를 거치지 않고도 부를 수 있으므로, 저장되는 값은 서버가 정합니다.
길이 제한과 문자 제한도 마찬가지로 서버에서 다시 봅니다.

`access_token` 은 재접속 인증 자격증명입니다. 원본은 발급 시 쿠키로 한 번만 내려주고
DB 에는 SHA-256 해시만 저장합니다.

### Answer: 참여자의 선택

한 참여자가 한 문항에 고른 보기(`A` 또는 `B`).
`participant_id` 와 `room_question_id` 로 가리키며 `room_id` 를 따로 담지 않습니다.

불변 규칙:

- 한 사람이 한 질문에 한 번만 답합니다: `UNIQUE (participant_id, room_question_id)`
- **제출된 답변은 수정할 수 없습니다** (PRD 9장, FR-06). INSERT 만 일어납니다
- 같은 제출 요청이 반복돼도 답변은 한 번만 저장됩니다 (PRD 14장).
  **다만 위 UNIQUE 는 안전망일 뿐 멱등성의 구현이 아닙니다.** 아래를 보십시오
- 참여자와 질문이 같은 방에 속하는지는 **DB 가 확인하지 않습니다.** 답변 저장 로직이 확인합니다

마지막 항목이 앱 책임인 이유는 `answer` 에 `room_id` 를 두지 않기 때문입니다.
넣고 복합 FK 를 걸면 DB 로 되지만 컬럼이 하나 늡니다 (`docs/database.md`).

#### 멱등성은 UNIQUE 로 달성되지 않습니다

위키 `API-규약.md` 의 "멱등성" 절이 요구하는 것은 두 가지입니다.

```text
같은 내용으로 재제출   최초 제출과 같은 성공 응답
다른 내용으로 재제출   409 ALREADY_SUBMITTED
```

**UNIQUE 제약은 둘 중 어느 것도 하지 못합니다.** 같은 내용인지 다른 내용인지 구분하지
못하고, 두 번째 요청의 첫 INSERT 에서 `1062` 가 나 트랜잭션이 통째로 롤백됩니다.
그대로 두면 재제출이 성공 응답도 409 도 아닌 **500** 이 됩니다.

**제출 로직이 INSERT 전에 판정해야 합니다.** `submitted_at IS NOT NULL` 이면 저장된
답변과 요청 내용을 비교해, 같으면 최초와 같은 성공 응답을, 다르면 `409` 를 돌려줍니다.
UNIQUE 는 그 판정을 빠져나간 동시 요청을 막는 마지막 안전망입니다.

**케미 점수는 `answer` 에서 조회 시 계산하는 파생 데이터입니다.** 저장하지 않습니다
(PRD 16장). 계산 규칙은 아래 "점수와 순위" 절에 있습니다.

## 관계

```text
Room        1 ──── N  RoomQuestion   방 생성 시 12개. room 삭제 시 CASCADE
Room        1 ──── N  Participant    room 삭제 시 RESTRICT (참여자가 있으면 방을 못 지움)
Question    1 ──── N  RoomQuestion   참조. question 삭제 시 RESTRICT
Participant 1 ──── N  Answer         participant 삭제 시 CASCADE
RoomQuestion 1 ─── N  Answer         room_question 삭제 시 CASCADE
```

**방장은 별도 관계가 아닙니다.** `participant.is_host` 로 표시합니다.
옛 설계의 `Room 1 ──── 1 Participant` (생성자) 관계는 없어졌습니다.
순환 참조와 복합 FK 가 함께 사라진 것이 그 결과입니다 (`docs/database.md`).

CASCADE 와 RESTRICT 가 섞인 것은 의도입니다. 파생 데이터는 따라 지워도 되지만
사람이 남긴 것은 실수로 지워지면 안 됩니다. 방을 지우는 순서는 `docs/database.md` 참고.

## 주요 흐름

### 방 생성

```text
1. room 생성            share_code 만 넣는다
2. participant 생성     방장. is_host = TRUE, submitted_at = NULL
3. room_question 생성   질문 12개를 무작위로 섞어 INSERT
```

**옛 설계의 4단계 중 `room.host_participant_id` 갱신이 사라졌습니다.** 방장이 누구인지가
참여자 행 안에 적히므로 방을 되짚어 갱신할 필요가 없습니다.

그래도 **셋 전체가 한 트랜잭션이어야 합니다.** 2번이 실패하면 방장 없는 방이,
3번이 실패하면 질문 없는 방이 남습니다. 둘 다 화면에서 복구할 방법이 없습니다.

응답에 담는 방 상태는 2번에서 만든 방장 행의 `submitted_at` 으로 계산합니다.
방 생성 직후에는 항상 `HOST_ANSWERING` 입니다.

#### 질문 12개 선정 규칙

위 3번 단계의 상세 규칙입니다.

| 항목 | 규칙 |
| --- | --- |
| 배분 | 카테고리 4개에서 각각 3개씩. 합쳐서 12개 |
| 후보 조건 | `active = TRUE` 인 질문만 |
| 추출 방식 | 카테고리 안에서 무작위 |
| 후보 부족 | 네 카테고리 중 하나라도 3개를 채우지 못하면 방 생성을 중단하고 **운영 오류로 기록합니다** (PRD 8장). 트랜잭션 전체를 롤백합니다 |
| 방 사이 중복 | 허용합니다. 방마다 독립적으로 뽑고 방장의 이전 방 이력을 보지 않습니다 |

후보 조회는 `question` 의 `idx_question_category_active (category, active)` 를 탑니다.

**후보가 모자라면 방을 만들지 않습니다.** 채워진 만큼만 만들면 방마다 질문 수가 달라져
케미 점수를 방끼리 비교할 수 없게 됩니다. 전체 점수 계산이 12로 나누는 것을 전제하므로
문항 수가 다르면 점수의 의미가 달라집니다. 위 RoomQuestion 절의 "방 하나는 질문 12개를
가집니다" 불변 규칙을 애플리케이션이 지키는 곳이 여기입니다. 운영 중에 질문을 잘못 비활성화하면
방 생성이 즉시 실패하므로, 질문을 내릴 때는 카테고리별 잔여 개수를 먼저 확인해야 합니다.

**방 사이 중복을 막지 않는 이유는 트랜잭션 크기입니다.** 직전 방과 다르게 뽑으려면 방 생성
시점에 방장의 이전 방 이력을 조회해야 하고, 그러면 한 트랜잭션에 `room`, `participant`,
`room_question` 이 아닌 테이블이 하나 더 들어옵니다. 같은 질문이 두 방에 나오는 것은
사용자에게 문제가 되지 않으므로 그 값을 치르지 않습니다.

한 방 안에서의 중복은 규칙이 아니라 DB 가 막습니다: `UNIQUE (room_id, question_id)`.

**뽑기는 실제로 무작위입니다.** 카테고리별 후보가 30개이고 그중 3개를 고르므로
방마다 다른 조합이 나옵니다. 시드를 12문항으로 되돌리면 후보와 필요 개수가 같아져
모든 방이 같은 질문을 받게 됩니다. 시드 규모를 줄일 때 이 점을 확인해야 합니다.

#### 문항 표시 순서

**완전 무작위입니다. 카테고리를 묶지 않습니다** (사용자 결정, PRD 7장 FR-03).

뽑은 12개를 섞어서 INSERT 하고, 읽을 때 `ORDER BY rq.id` 로 그 순서를 되살립니다.
카테고리 4개에서 3개씩 뽑는 것은 **배분 규칙이고 화면에 보이는 순서와 무관합니다.**
대화 질문 다음에 소비 질문이 나올 수 있습니다.

**한 방 안에서는 모든 참여자가 같은 순서로 봅니다.** 순서가 INSERT 시점에 정해지므로
참여자마다 다시 섞지 않습니다. 방마다는 다릅니다.

옛 설계는 `display_order` 컬럼에 카테고리 묶음 순서(1~3 대화, 4~6 여행, 7~9 생활,
10~12 소비)를 부여했습니다. **컬럼과 규칙이 함께 없어졌습니다.** 되살리지 마십시오.

컬럼을 없앤 대가로 `id` 가 식별자이면서 순서이기도 합니다. 화면의 "3/12" 도
앱이 세야 합니다. 방 안에서 몇 번째인지가 스키마에 선언돼 있지 않습니다.

#### share_code 생성 규칙

`ShareCodeGenerator` 가 `SecureRandom` 으로 16바이트(128비트)를 뽑아 패딩 없는
base64url 로 인코딩합니다. 결과는 22자입니다. `share_code` 는 `VARCHAR(32)` 라 여유가 있습니다.

`java.util.Random` 을 쓰지 않습니다. 방 접근 수단이 이 코드 하나뿐이라 코드를 맞히면
방에 들어올 수 있고, 그래서 자격증명에 준합니다. 로그에 남기지 않습니다.

URL 경로에 그대로 들어가므로 `+` 와 `/` 가 없는 base64url 이어야 인코딩이 필요 없습니다.
충돌은 재시도하지 않습니다. `uk_room_share_code` 가 거절하면 500 으로 나갑니다.

### 답변 제출

```text
answer 12행 INSERT
participant.submitted_at = NOW(6)
```

**갱신하는 상태 컬럼이 없습니다.** 옛 설계의 `participant.answer_status = SUBMITTED` 는
`submitted_at` 하나로 판단하게 되어 사라졌습니다.

둘이 한 트랜잭션이어야 합니다. 부분 적용되면 답을 다 내지 않은 사람이 제출한 것으로
보이거나, 답은 저장됐는데 제출로 집계되지 않습니다.

**제출자가 방장이면 그 방이 `OPEN` 이 됩니다.** 별도로 갱신하는 것이 아니라
위 한 줄의 결과입니다. 일반 참여자의 제출도 같은 두 단계이고, 방 상태에 영향이 없다는
것만 다릅니다.

## 점수와 순위

**PRD 10장에 확정돼 있습니다.** 저장하지 않고 조회할 때 `answer` 에서 계산합니다 (PRD 16장).

```text
전체 케미 점수      = (두 참여자의 일치 답변 수 / 12) x 100    소수점 반올림
카테고리 케미 점수   = (해당 카테고리의 일치 답변 수 / 3) x 100
```

카테고리는 `room_question` 이 참조하는 `question.category` 로 판정합니다.

- 답변을 완료한 참여자가 2명 이상이면 Pair 결과를 계산합니다 (FR-07)
- 3명 이상이면 모든 Pair 를 계산해 그룹 순위를 제공합니다 (FR-08)
- 순위는 점수 내림차순. 같으면 공동 순위입니다
- Pair 내부의 A 와 B 는 **정규화된 닉네임 오름차순으로 고정합니다.**
  공동 순위 내부도 같은 기준으로 안정 정렬하며, 이 정렬은 표시 순서만 정하고
  공동 순위를 나누지 않습니다

`반전 케미 조합` 선정 규칙과 화면 구성은 PRD 10장, 11장에 있습니다.
**응답에 모든 Pair 를 담지 않습니다.** 근거는 PRD 11장입니다.
