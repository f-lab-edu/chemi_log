# Domain

케미로그의 비즈니스 개념과 불변 규칙을 정리합니다.

**이 문서의 기준은 `database/init/01-schema.sql`과 PRD입니다.**  
백엔드 도메인 코드는 이 기준으로 다시 작성했습니다.  
전체 배치는 `docs/architecture.md`를 참고합니다.

ERD 재설계에서 방 상태와 제출 상태를 저장 컬럼이 아니라 파생값으로 바꿨고,
질문 스냅샷도 값 복사 방식에서 참조 방식으로 변경했습니다. 자세한 근거는 `docs/database.md`에 있습니다.

서비스 개요: 여러 명이 같은 질문에 각자 답하고, 답변을 비교해 서로의 케미 점수와
모임 안 관계 순위를 확인합니다 (`README.md`).

## 개념

### Question: 원본 질문 (Master)

서비스가 보유한 질문 Pool입니다. 방과 관계없이 존재합니다.

| 속성 | 값 |
| --- | --- |
| `category` | `CONVERSATION` / `TRAVEL` / `LIFESTYLE` / `SPENDING` |
| `content` | 질문 본문 |
| `option_a`, `option_b` | 2지선다 보기 |
| `active` | 방 생성 시 후보로 사용할지 여부 |

불변 규칙:

- 한 카테고리 안에서 `content`는 유일합니다: `UNIQUE (category, content)`.
  시드를 두 번 적용하면 이 제약에서 막힙니다. 이 제약이 없으면 같은 문항이 새 `id`로 들어가
  한 방에 같은 질문이 두 번 나올 수 있습니다 (`docs/database.md`).

현재 시드는 카테고리별 30문항, 총 120문항입니다 (`database/init/02-seed.sql`).
카테고리마다 성향 6개를 정해 5문항씩 배분했습니다. **질문을 추가할 때도 이 배분을 유지해야 합니다.**
카테고리 점수를 3문항으로 계산하기 때문에 30개가 모두 같은 성향을 묻는 질문이면,
어느 3개를 뽑아도 결과가 비슷해지고 점수가 0점 또는 100점 쪽으로 몰릴 수 있습니다.
자세한 근거는 시드 파일 머리말에 있습니다.

**한 번 넣은 질문의 `category`, `content`, `option_a`, `option_b`는 수정하지 않습니다.**
문구를 바꾸려면 새 행을 추가하고 기존 행은 `active = FALSE`로 내립니다.
이 전제를 두고 `room_question`은 질문 값을 복사하지 않고 원본을 참조합니다.

DB가 이 불변 규칙 자체를 강제하지는 않습니다. 근거와 검토 과정은 `docs/database.md`의
"질문은 불변입니다"를 참고합니다. **해당 절은 임의 수정 금지 대상입니다.**

`active = FALSE`로 내려도 행 자체는 남기 때문에, 그 질문을 사용하던 기존 방에는 그대로 보입니다.

### Room: 케미방

한 번의 케미 측정 단위입니다. 공유 코드로 접근합니다.

**방이 직접 저장하는 고유한 사실은 공유 코드뿐이며 상태 컬럼은 없습니다.**

| 상태 | 의미 | 어떻게 판정하나 |
| --- | --- | --- |
| `HOST_ANSWERING` | 방이 만들어졌고 방장이 아직 답변 중인 상태. 다른 사람은 참여할 수 없습니다 | 방장의 `submitted_at IS NULL` |
| `OPEN` | 방장이 답변 제출을 마쳐 참여자를 받을 수 있는 상태 | 방장의 `submitted_at IS NOT NULL` |

상태를 DB에 저장하지 않을 뿐, 도메인 개념 자체가 사라진 것은 아닙니다.
API 응답에는 위 두 값을 그대로 담습니다 (PRD 7장, 20장).
프론트엔드는 API 응답만 보기 때문에 상태가 저장값인지 파생값인지는 알 필요가 없습니다.

정상 상태 전이는 하나뿐입니다.

```text
HOST_ANSWERING  →  OPEN
```

역방향 전이나 그 외 상태는 현재 설계에 없습니다. 필요해 보이더라도 임의로 추가하지 않습니다.

`OPEN`으로의 전이는 **방장이 답변 제출을 완료한 뒤에만** 일어납니다 (PRD 5장).
이 전이를 위해 실제로 갱신하는 컬럼은 방장의 `participant.submitted_at` 하나입니다.

이전 설계에서는 `room.status`와 `participant.answer_status`를 함께 갱신해야 했습니다.
두 값이 서로 다른 테이블에 있어 DB CHECK로 묶을 수도 없었고,
한쪽만 반영되면 방장은 답변을 끝냈는데 친구는 여전히 "방장이 준비 중" 화면에 막힐 수 있었습니다.

현재는 상태 판단의 기준이 `submitted_at` 하나이므로 서로 어긋날 값 자체가 없습니다.

### RoomQuestion: 방에 고정된 질문 12개

질문 값을 복사하지 않고 `question`을 참조합니다 (`room_id`, `question_id`).

PRD 8장은 이미 만들어진 방의 질문과 결과가 바뀌지 않아야 한다고 요구합니다.
**원본 질문을 수정하지 않으므로** 참조 방식으로도 이 요구를 지킬 수 있습니다.
위 Question 절의 불변 규칙이 이 설계의 전제입니다.

불변 규칙:

- 한 방에 같은 질문이 두 번 들어가지 않습니다: `UNIQUE (room_id, question_id)`.
- 방 하나는 질문 12개를 가집니다. **질문 개수 12는 DB가 보장하지 않습니다.**
  방 생성 트랜잭션과 테스트에서 확인해야 합니다.
- 표시 순서 컬럼은 없습니다. 질문 순서는 `id` 오름차순입니다.
  **조회할 때 `ORDER BY rq.id`를 빠뜨리면 순서를 보장할 수 없습니다.**
- 방의 질문을 조회할 때 `question`과 **조인해도 됩니다.**
  질문 자체가 불변이므로 기존 방에 수정된 문구가 붙는 문제가 없습니다.

마지막 항목은 이전 설계와 반대입니다.
이전에는 질문 값을 방에 복사해 두고 "원본 질문과 다시 조인하지 않는다"는 규칙으로 스냅샷을 유지했습니다.
하지만 이 규칙은 DB로 강제할 수 없었습니다. 현재 구조에서는 질문 자체를 불변으로 두고 참조합니다.

### Participant: 참여자

방에 들어온 사람입니다. 방장도 참여자이며, `is_host = TRUE`인 행이 방장입니다.

| 상태 | 의미 | 어떻게 판정하나 |
| --- | --- | --- |
| `ANSWERING` | 답변 작성 중 | `submitted_at IS NULL` |
| `SUBMITTED` | 답변 제출 완료 | `submitted_at IS NOT NULL` |

Room 상태와 마찬가지로 상태 컬럼을 따로 저장하지 않고, API 응답에서는 위 상태값을 그대로 사용합니다.

불변 규칙:

- 한 방 안에서 닉네임은 중복될 수 없습니다: `UNIQUE (room_id, nickname_key)`.
- 방마다 방장은 한 명입니다. **DB가 직접 강제하지 않습니다.**
  `is_host = TRUE`를 만드는 곳이 방 생성 한 군데뿐이고,
  링크로 들어오는 참여자는 항상 `FALSE`로 생성됩니다.
- `submitted_at`은 `NOW(6)`로 채웁니다.
  앱에서 `LocalDateTime.now()`를 사용하면 `created_at`과 시간 기준이 달라질 수 있습니다.
  `DATETIME`은 시간대 정보를 담지 않기 때문에 JVM이 UTC인 컨테이너에서는
  9시간 이른 값이 들어가도 DB가 오류를 내지 않습니다.

닉네임은 표시용 `nickname`과 중복 판정용 `nickname_key`로 나눕니다.

정규화는 trim, 연속 공백 축소, NFC, 공백 전체 제거, `toLowerCase(Locale.ROOT)` 순서로 처리하고
**전부 애플리케이션에서 수행합니다.**

`Locale` 인자를 생략하면 터키어 로케일에서 `I`가 `ı`로 바뀌는 것처럼
실행 환경에 따라 결과가 달라질 수 있습니다.

**공백 전체 제거는 `nickname_key`에만 적용합니다.**
표시용 `nickname`에는 내부 공백을 남깁니다.

PRD 7장에서 공백 제거를 중복 판정에만 적용하도록 나눠 두었습니다.
`지 은`으로 입력한 사용자는 화면에서도 `지 은`으로 보이지만,
중복 판정에서는 `지은`과 같은 닉네임으로 취급합니다.

사전 중복 조회에서 이 정규화를 빠뜨리면 `min su`와 `minsu`를 서로 다른 이름으로 통과시킨 뒤
INSERT 시점에 `UNIQUE (room_id, nickname_key)` 위반이 발생할 수 있습니다.
이 경우 의도한 409가 아니라 500으로 이어질 수 있습니다.

**프론트엔드에서도 trim과 연속 공백 축소를 하지만 서버는 그 결과를 신뢰하지 않습니다.**
프론트의 정규화는 입력 결과를 사용자에게 미리 보여주기 위한 용도입니다.

`POST /api/rooms`는 브라우저를 거치지 않고도 호출할 수 있으므로,
실제로 저장되는 값은 서버가 최종적으로 정합니다.
길이 제한과 문자 제한도 같은 이유로 서버에서 다시 확인합니다.

`access_token`은 재접속 인증에 사용하는 자격증명입니다.
원본 토큰은 발급 시 쿠키로 한 번만 내려주고, DB에는 SHA-256 해시만 저장합니다.

### Answer: 참여자의 선택

한 참여자가 한 문항에 고른 보기입니다 (`A` 또는 `B`).

`participant_id`와 `room_question_id`로 대상을 가리키고,
`room_id`는 별도로 저장하지 않습니다.

불변 규칙:

- 한 사람이 한 질문에는 한 번만 답합니다: `UNIQUE (participant_id, room_question_id)`.
- **제출된 답변은 수정할 수 없습니다** (PRD 9장, FR-06). INSERT만 일어납니다.
- 같은 제출 요청이 반복되어도 답변은 한 번만 저장됩니다 (PRD 14장).
  **다만 위 UNIQUE는 안전망일 뿐 멱등성 자체를 구현하는 수단은 아닙니다.**
- 참여자와 질문이 같은 방에 속하는지는 **DB가 확인하지 않습니다.**
  답변 저장 로직에서 확인합니다.

마지막 규칙은 애플리케이션 책임입니다. `answer`에 `room_id`를 두지 않았습니다.
`room_id`를 추가하고 복합 FK를 만들면 DB에서 보장할 수 있지만 컬럼이 하나 늘어납니다 (`docs/database.md`).

#### 멱등성은 UNIQUE로 달성되지 않습니다

위키 `API-규약.md`의 "멱등성" 절에서 요구하는 동작은 다음 두 가지입니다.

```text
같은 내용으로 재제출   최초 제출과 같은 성공 응답
다른 내용으로 재제출   409 ALREADY_SUBMITTED
```

UNIQUE 제약만으로는 두 경우를 구분할 수 없습니다.
같은 내용인지 다른 내용인지 판단하지 못하고,
두 번째 요청의 첫 INSERT에서 `1062`가 발생하면 트랜잭션 전체가 롤백됩니다.

그대로 두면 재제출 요청이 성공도 409도 아닌 500으로 처리될 수 있습니다.

따라서 **INSERT 전에 제출 여부와 기존 답변을 먼저 확인해야 합니다.**

`submitted_at IS NOT NULL`이면 저장된 답변과 새 요청을 비교합니다.

- 내용이 같으면 최초 제출과 같은 성공 응답
- 내용이 다르면 `409 ALREADY_SUBMITTED`

UNIQUE 제약은 이 판정을 구현하는 수단이 아니라,
동시 요청 등으로 애플리케이션 로직을 빠져나간 중복 저장을 막는 마지막 안전망입니다.

**케미 점수는 `answer`에서 조회 시 계산하는 파생 데이터이며 별도로 저장하지 않습니다**
(PRD 16장). 계산 규칙은 아래 "점수와 순위" 절에 있습니다.

## 관계

```text
Room         1 ──── N  RoomQuestion   방 생성 시 12개. room 삭제 시 CASCADE
Room         1 ──── N  Participant    room 삭제 시 RESTRICT (참여자가 있으면 방을 못 지움)
Question     1 ──── N  RoomQuestion   참조. question 삭제 시 RESTRICT
Participant  1 ──── N  Answer         participant 삭제 시 CASCADE
RoomQuestion 1 ──── N  Answer         room_question 삭제 시 CASCADE
```

방장은 별도의 관계로 두지 않습니다. `participant.is_host`로 표시합니다.

이전 설계의 `Room 1 ──── 1 Participant` 생성자 관계는 제거했습니다.
그 결과 순환 참조와 복합 FK도 함께 없어졌습니다 (`docs/database.md`).

CASCADE와 RESTRICT를 섞어 사용한 것은 의도한 설계입니다.
파생 데이터는 부모와 함께 지워도 되지만, 사람이 남긴 데이터는 실수로 함께 지워지지 않도록 했습니다.
방 삭제 순서는 `docs/database.md`를 참고합니다.

## 주요 흐름

### 방 생성

```text
1. room 생성            share_code만 넣는다
2. participant 생성     방장. is_host = TRUE, submitted_at = NULL
3. room_question 생성   질문 12개를 무작위로 섞어 INSERT
```

이전 설계의 4단계 중 `room.host_participant_id` 갱신 단계가 없어졌습니다.
방장 정보가 참여자 행 자체에 있으므로 방을 다시 갱신할 필요가 없습니다.

다만 **세 단계 전체는 반드시 하나의 트랜잭션이어야 합니다.**

2번이 실패하면 방장 없는 방이 남고,
3번이 실패하면 질문이 없는 방이 남습니다.
두 경우 모두 정상적인 화면 흐름에서 복구할 방법이 없습니다.

응답에 담는 방 상태는 2번에서 생성한 방장 참여자의 `submitted_at`으로 계산합니다.
방 생성 직후에는 항상 `HOST_ANSWERING`입니다.

#### 질문 12개 선정 규칙

위 3번 단계의 상세 규칙입니다.

| 항목 | 규칙 |
| --- | --- |
| 배분 | 카테고리 4개에서 각각 3개씩. 합쳐서 12개 |
| 후보 조건 | `active = TRUE`인 질문만 사용 |
| 추출 방식 | 카테고리 안에서 무작위 |
| 후보 부족 | 네 카테고리 중 하나라도 3개를 채우지 못하면 방 생성을 중단하고 **운영 오류로 기록합니다** (PRD 8장). 트랜잭션 전체를 롤백합니다 |
| 방 사이 중복 | 허용합니다. 방마다 독립적으로 뽑고 방장의 이전 방 이력은 보지 않습니다 |

후보 조회는 `question`의 `idx_question_category_active (category, active)` 인덱스를 사용합니다.

**후보가 부족하면 방을 만들지 않습니다.**

부족한 만큼만 넣어 방을 만들면 방마다 질문 수가 달라지고,
전체 케미 점수를 12문항 기준으로 계산한다는 전제가 깨집니다.
문항 수가 달라지면 같은 점수라도 의미가 달라질 수 있습니다.

위 RoomQuestion 절의 "방 하나는 질문 12개를 가진다"는 규칙을
애플리케이션에서 보장하는 곳이 바로 방 생성 로직입니다.

운영 중 질문을 비활성화할 때는 카테고리별 활성 질문이 최소 3개 이상 남는지 먼저 확인해야 합니다.

방 사이 질문 중복은 허용합니다.
직전 방과 다른 질문을 고르려면 방 생성 시점에 방장의 과거 방 이력을 추가로 조회해야 하고,
트랜잭션 범위도 넓어집니다.

현재 서비스에서는 같은 질문이 서로 다른 방에 다시 나오는 것을 문제로 보지 않기 때문에
이전 방 이력까지 조회하지 않습니다.

한 방 안에서 같은 질문이 두 번 들어가는 것은 DB가 막습니다:
`UNIQUE (room_id, question_id)`.

질문 선택은 실제로 무작위입니다.
카테고리별 후보가 30개이고 그중 3개를 고르기 때문에 방마다 다른 조합이 나올 수 있습니다.

시드를 12문항 수준으로 줄이면 후보 수와 필요한 수가 같아져
모든 방이 거의 같은 질문을 받게 됩니다. 시드 규모를 줄일 때는 이 점을 함께 확인해야 합니다.

#### 문항 표시 순서

문항 순서는 **완전 무작위이며 카테고리별로 묶지 않습니다**
(사용자 결정, PRD 7장 FR-03).

선정한 12개 질문을 섞은 순서대로 INSERT하고,
조회할 때 `ORDER BY rq.id`로 같은 순서를 다시 읽습니다.

카테고리별로 3개씩 뽑는 것은 배분 규칙일 뿐,
화면에 표시되는 순서와는 관계가 없습니다.
대화 질문 다음에 소비 질문이 나올 수도 있습니다.

한 방 안에서는 모든 참여자가 같은 질문 순서를 봅니다.
순서가 방 생성 시 INSERT 순서로 한 번 정해지기 때문에 참여자마다 다시 섞지 않습니다.
대신 방마다 순서는 달라질 수 있습니다.

이전 설계에서는 `display_order` 컬럼에
카테고리별 고정 순서(1~3 대화, 4~6 여행, 7~9 생활, 10~12 소비)를 넣었습니다.
현재는 해당 컬럼과 규칙 모두 제거했습니다.

대신 `id`가 식별자이면서 표시 순서 역할도 합니다.
화면의 "3/12" 같은 값은 애플리케이션에서 계산합니다.
방 안에서 몇 번째 질문인지는 스키마에 별도 컬럼으로 선언되어 있지 않습니다.

#### share_code 생성 규칙

`ShareCodeGenerator`는 `SecureRandom`으로 16바이트(128비트)를 생성한 뒤,
패딩 없는 Base64URL로 인코딩합니다. 결과는 22자입니다.

`share_code`는 `VARCHAR(32)`이므로 길이에는 여유가 있습니다.

`java.util.Random`은 사용하지 않습니다.
현재 방 접근 수단이 공유 코드 하나뿐이기 때문에,
공유 코드를 추측할 수 있으면 방에 접근할 수 있습니다.
따라서 자격증명에 준해서 다루고 로그에도 남기지 않습니다.

URL 경로에 그대로 들어가기 때문에 `+`, `/`가 없는 Base64URL을 사용합니다.
별도의 URL 인코딩 없이 경로에 넣을 수 있습니다.

충돌 시 애플리케이션에서 별도 재시도는 하지 않습니다.
`uk_room_share_code` 제약에서 충돌이 발생하면 서버 오류로 처리합니다.

### 답변 제출

```text
answer 12행 INSERT
participant.submitted_at = NOW(6)
```

별도로 갱신하는 상태 컬럼은 없습니다.
이전 설계의 `participant.answer_status = SUBMITTED`는 제거했고,
현재는 `submitted_at` 하나로 제출 상태를 판단합니다.

두 작업은 하나의 트랜잭션으로 처리해야 합니다.

부분 적용되면 답변을 다 저장하지 못했는데 제출 완료로 보이거나,
답변은 저장됐지만 제출자로 집계되지 않는 상태가 생길 수 있습니다.

제출자가 방장이면 이 작업이 끝난 뒤 방 상태가 `OPEN`이 됩니다.
별도의 `room.status`를 갱신하는 것이 아니라,
방장의 `submitted_at`이 채워진 결과로 상태가 바뀝니다.

일반 참여자의 제출도 같은 두 단계로 처리하지만,
방 상태에는 영향을 주지 않습니다.

## 점수와 순위

점수 계산 규칙은 PRD 10장에 정의되어 있습니다.
점수는 DB에 저장하지 않고 조회 시 `answer`에서 계산합니다 (PRD 16장).

```text
전체 케미 점수      = (두 참여자의 일치 답변 수 / 12) x 100    소수점 반올림
카테고리 케미 점수  = (해당 카테고리의 일치 답변 수 / 3) x 100
```

카테고리는 `room_question`이 참조하는 `question.category`로 판단합니다.

- 답변을 완료한 참여자가 2명 이상이면 Pair 결과를 계산합니다 (FR-07).
- 3명 이상이면 모든 Pair를 계산해 그룹 순위를 제공합니다 (FR-08).
- 순위는 점수 내림차순입니다. 점수가 같으면 공동 순위입니다.
- Pair 내부의 A와 B는 **정규화된 닉네임 오름차순으로 고정합니다.**
  공동 순위 안에서도 같은 기준으로 안정 정렬합니다.
  이 정렬은 표시 순서만 결정하며 공동 순위 자체를 나누지는 않습니다.

`반전 케미 조합` 선정 규칙과 화면 구성은 PRD 10장, 11장에 있습니다.

**응답에 모든 Pair를 담지는 않습니다.**
자세한 응답 범위는 PRD 11장을 따릅니다.
