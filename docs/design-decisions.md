# 설계 결정 기록

케미로그 백엔드에서 내린 설계 결정과 그 이유를 기록합니다.

다른 `docs/` 문서가 "현재 어떻게 구현되어 있는가"를 설명한다면, 이 문서는 "왜 이 방식을 선택했는가"를 남기는 문서입니다.

각 항목에는 먼저 결정을 적고, 그 아래에 결정하게 된 이유를 적습니다. 검토한 다른 방법들은 선택지 표에 함께 정리해 각각의 장점과 단점을 비교합니다. 표에서 고른 방식은 굵게 표시합니다. 마지막에는 현재 선택으로 생기는 제약과 앞으로 지켜야 할 사항을 남깁니다.

이미 구현된 내용과 앞으로 구현할 내용 모두 포함하며, 상태는 각 항목 제목에 표시합니다.

- `[구현됨]` 코드가 있고 테스트를 통과한 상태입니다.
- `[확정됨]` 결정은 끝났고 구현은 다음 이슈에서 진행합니다.
- `[대기]` 선택지 검토까지 끝났고 최종 결정을 기다리는 상태입니다.

세부 구현이나 규칙이 다른 문서에 이미 정리되어 있다면 해당 문서를 가리키고, 여기에는 설계 판단과 그 이유만 적습니다.

## 1. 인증: 회원가입 없이 방별 참여자 토큰 [구현됨]

방마다 따로 발급하는 불투명 토큰을 사용합니다.

참여자를 만들 때 32바이트 난수를 Base64URL로 인코딩해 쿠키로 한 번 전달하고, DB에는 SHA-256 해시(`participant.access_token_hash`, `BINARY(32)`)만 저장합니다. 요청이 들어오면 쿠키의 토큰을 다시 해시해 참여자를 찾고, 찾은 참여자의 `room_id`가 요청 경로의 방과 같은지 확인합니다.

이 서비스에서 식별해야 하는 대상은 "사용자"가 아니라 "이 방에 참여한 이 참여자"입니다. 참여자 하나를 식별하는 것이 목적이므로 별도의 회원 계정이나 로그인 세션까지 둘 필요가 없다고 판단했습니다.

PRD 16장에서도 회원가입, 이메일, 전화번호, 소셜 로그인을 받지 않기로 했습니다. 초대 링크로 들어와 닉네임만 입력하고 바로 참여하는 흐름이기 때문에 로그인 절차는 제품 구조와도 맞지 않습니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 로그인 (ID·비밀번호 또는 소셜) | 사용자를 장기적으로 식별할 수 있어 "내가 참여한 방", 케미 기록 같은 기능으로 확장하기 쉽습니다. 계정을 통한 복구 수단도 만들 수 있습니다. | 현재 PRD 범위와 맞지 않습니다. 짧게 참여하는 서비스에 가입 절차가 추가되고, 비밀번호 관리·소셜 로그인 연동·개인정보 처리까지 함께 필요해집니다. |
| 서버 세션 (`HttpSession`) | Spring에서 기본적으로 지원하고, 서버에서 세션을 삭제하면 바로 무효화할 수 있습니다. | 한 브라우저에서 여러 방의 자격을 따로 유지하려면 세션 안에 방별 정보를 별도로 관리해야 합니다. 서버를 여러 대로 늘릴 경우 세션 저장소도 필요합니다. |
| JWT | 서버에 세션을 저장하지 않고 토큰 자체를 검증할 수 있습니다. 서버가 여러 대여도 별도의 세션 공유가 필요 없습니다. | 이 서비스에서는 매 요청마다 참여자를 조회해 방 소속과 제출 여부를 확인해야 합니다. 결국 DB 조회가 필요하므로 JWT의 stateless한 장점을 크게 활용하지 못합니다. 즉시 무효화가 어렵고 서명 키 관리도 추가됩니다. |
| **방별 불투명 토큰 + DB 해시** | 토큰 하나가 특정 방의 특정 참여자 하나와 직접 대응합니다. DB에는 해시만 저장하므로 원본 토큰을 남기지 않아도 되고, 참여자 행을 삭제하면 해당 토큰도 바로 사용할 수 없게 됩니다. | 토큰을 잃으면 기존 자격을 복구할 수 없습니다. 방을 넘어 사용자를 식별하는 개념도 없기 때문에 장기적인 케미 기록 기능에는 별도의 식별 방식이 필요합니다. |

JWT는 서버에 상태를 저장하지 않고 검증할 수 있다는 장점이 있습니다. 하지만 이 서비스에서는 어차피 참여자의 방 소속과 제출 상태를 확인하기 위해 DB를 조회해야 합니다. 그래서 JWT를 사용해도 DB 조회를 없앨 수 없고, 즉시 무효화가 어렵다는 점과 서명 키 관리만 추가됩니다.

DB에 토큰 원문 대신 해시를 저장하는 이유는 토큰 자체를 DB에 남기지 않기 위해서입니다. 다만 토큰이 256비트 난수이므로 비밀번호처럼 사전 공격을 고려할 필요는 없습니다. bcrypt 같은 느린 해시를 사용할 이유는 없고 SHA-256이면 충분합니다.

현재 방식에서는 토큰을 잃으면 기존 참여자 자격을 복구할 수 없습니다. 다시 참여하려면 새로운 참여자로 들어와야 하며, 이 부분은 PRD 16장에서 허용한 범위입니다.

또한 방을 가로지르는 사용자 식별자가 없기 때문에 "내가 참여한 방 목록" 같은 기능도 바로 만들 수 없습니다. 이후 장기 케미 기록이 필요해지면 선택형 가입이나 기기 식별 등 별도의 식별 전략을 추가로 결정합니다.

근거: `docs/database.md` "참여자 토큰은 해시로 저장합니다", 위키 API 규약 인증 절.

## 2. 토큰을 어디에 두나: HttpOnly 쿠키 [구현됨]

참여자 토큰은 `HttpOnly; Secure; SameSite=Lax` 쿠키에 담고, `Path`로 방별 범위를 나눕니다.

```text
Set-Cookie: participantToken=...; HttpOnly; Secure; SameSite=Lax;
            Path=/api/rooms/{shareCode}; Max-Age=34560000
```

이 서비스의 참여자 자격은 최대 400일 동안 유지됩니다. 토큰이 한 번 유출되면 오랫동안 사용할 수 있기 때문에, XSS가 발생하더라도 토큰 자체는 JavaScript에서 읽을 수 없도록 하는 쪽을 선택했습니다. 그 역할을 하는 것이 `HttpOnly`입니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| localStorage + Authorization 헤더 | 프론트가 토큰을 직접 읽을 수 있어 "내가 누구인지"를 스스로 알 수 있습니다. 브라우저가 자동으로 인증 정보를 붙이지 않기 때문에 일반적인 CSRF 공격도 성립하지 않습니다. | JavaScript에서 토큰을 읽을 수 있어 XSS가 발생하면 토큰이 그대로 노출됩니다. 닉네임이 사용자 입력이라 XSS 표면도 있습니다. 방별 토큰 보관도 프론트에서 직접 관리해야 합니다. |
| 응답 바디로 주고 프론트가 보관 | 프론트가 토큰을 직접 관리할 수 있습니다. | 결국 localStorage 같은 JavaScript 접근 가능한 저장소를 사용해야 하므로 `HttpOnly`를 적용할 수 없습니다. |
| 초대 링크 URL에 토큰 포함 | 별도 저장소가 필요 없고 링크만 있으면 자격을 복구할 수 있습니다. | 링크를 다른 사람에게 공유하는 순간 참여자 자격까지 같이 전달됩니다. 초대 링크는 다른 사람에게 보내는 값이므로 이 방식과 맞지 않습니다. 브라우저 히스토리나 서버 로그에도 남을 수 있습니다. |
| **HttpOnly; Secure; SameSite=Lax 쿠키** | JavaScript에서 토큰을 읽을 수 없어 XSS가 발생해도 토큰 탈취 위험을 줄일 수 있습니다. 브라우저가 자동으로 저장하고 전송하며, `Path`를 이용해 방별로 나눌 수 있습니다. | 프론트가 토큰을 직접 읽을 수 없으므로 "내가 누구인지"를 서버가 알려줘야 합니다. CSRF는 SameSite 정책으로 막아야 하고, `Secure`를 사용하므로 운영 환경은 HTTPS여야 합니다. |

localStorage 방식에서 얻을 수 있는 CSRF 방어는 `SameSite=Lax`로 대신합니다. 다른 사이트에서 시작된 일반적인 POST 요청에는 해당 쿠키가 전송되지 않습니다.

`Secure`는 개발 환경에서도 빼지 않습니다. 브라우저가 `http://localhost`를 신뢰 가능한 컨텍스트로 취급하므로 개발 환경에서 별도로 제거할 필요가 없습니다. 개발에서만 설정을 다르게 두면 운영 배포 후 처음 드러나는 차이가 생길 수 있습니다.

프론트는 토큰을 직접 읽을 수 없으므로 방 요약 API가 `me` 필드를 통해 현재 참여자를 알려줘야 합니다. `CreatedRoom`과 `CreateRoomResponse`를 나눈 것도 이 결정과 연결됩니다. 토큰은 응답 바디가 아니라 `Set-Cookie` 헤더로 전달되기 때문에 응답 DTO에는 토큰 필드가 없습니다.

근거: `docs/conventions.md` "서비스가 컨트롤러에 돌려주는 값도 응답 DTO와 분리합니다".

## 3. 방마다 다른 쿠키: 이름이 아니라 Path로 나눔 [구현됨]

쿠키 이름은 하나로 두고 `Path=/api/rooms/{code}`로 방을 나눕니다.

쿠키는 이름 하나만으로 구분되지 않고 이름, 도메인, Path의 조합으로 구분됩니다. 이름이 같더라도 Path가 다르면 별개의 쿠키로 저장되고 서로 덮어쓰지 않습니다.

한 브라우저에서 방 A와 방 B에 각각 참여할 수 있고, 각 방의 자격을 따로 유지해야 합니다. 쿠키 하나에 `Path=/`를 사용하면 방 B 참여 시 방 A의 쿠키가 덮어써집니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 이름에 방 코드를 붙임 (`participantToken_{code}`, `Path=/`) | 어느 경로에서든 모든 방의 자격을 읽을 수 있습니다. 구현 방식도 직관적입니다. | 모든 요청에 모든 방의 쿠키가 같이 전송됩니다. 방이 많아질수록 요청 헤더가 계속 커지고, 서버도 경로 변수에 맞춰 쿠키 이름을 조립해야 합니다. |
| 쿠키 하나에 여러 방의 토큰을 담음 (JSON 등) | 쿠키 개수가 하나로 유지됩니다. | 새 방에 참여할 때마다 기존 값을 읽어 병합한 뒤 다시 저장해야 합니다. 단일 쿠키의 크기 제한에도 닿을 수 있고, 한 방의 토큰만 바뀌어도 전체 값을 다시 써야 합니다. |
| **이름은 하나, `Path=/api/rooms/{code}`** | 브라우저가 해당 방 경로로 가는 요청에만 해당 방의 쿠키를 전송합니다. 헤더가 불필요하게 커지지 않고 서버도 쿠키 이름 하나만 알면 됩니다. | 방 경로 밖에서는 해당 자격을 읽을 수 없습니다. 자격이 필요한 API를 모두 그 경로 아래에 두어야 합니다. |

Path 방식의 제약은 방 경로 밖에서 자격을 읽을 수 없다는 점입니다. 하지만 PRD에서 "내가 참여한 방 목록"을 제공하지 않기로 했기 때문에 현재 기능에서는 문제가 되지 않습니다.

반대로 방마다 쿠키 이름을 다르게 두면 참여한 방이 많아질수록 요청 헤더가 커집니다. 하나의 쿠키에 여러 토큰을 합치는 방식은 서버에서 병합 로직을 따로 관리해야 합니다.

자격이 필요한 엔드포인트는 앞으로도 모두 `/api/rooms/{shareCode}` 아래에 둡니다.

또한 `Path`는 브라우저가 어떤 쿠키를 보낼지 정하는 규칙일 뿐, 서버의 권한 검사가 아닙니다. `curl` 같은 클라이언트는 임의의 쿠키를 어떤 경로에도 보낼 수 있습니다.

그래서 서버는 토큰으로 찾은 참여자의 `room_id`와 요청 경로의 방이 같은지 매 요청마다 확인합니다. `AC-SEC-ROOM-ISOLATION`에서 실제 보안 경계가 되는 부분은 이 검사입니다.

## 4. 자격 수명: 400일 [구현됨]

쿠키의 `Max-Age`는 400일로 둡니다.

PRD는 "브라우저 사이트 데이터를 지울 때까지" 자격을 유지하라고 합니다. 하지만 실제 브라우저에는 무기한 유지되는 영구 쿠키가 없어서, 가능한 범위에서 가장 긴 수명을 사용합니다.

Chrome 계열은 쿠키의 최대 수명을 400일로 제한하므로 그보다 긴 값을 넣어도 실질적인 차이가 없습니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 세션 쿠키 (`Max-Age` 없음) | 브라우저를 닫으면 자격이 사라져 공용 PC에서는 더 안전합니다. | 브라우저를 종료했다 다시 연 사용자가 기존 방으로 돌아오지 못합니다. `AC-TOKEN-RESTART` 요구와 맞지 않습니다. 위키 예시가 한때 이 형태였고 그대로 구현했다가 리뷰에서 발견됐습니다. |
| 짧은 수명 + 갱신 API | 토큰이 유출되더라도 오래 사용할 수 없습니다. | 갱신 시점을 프론트에서 관리해야 합니다. 갱신 전에 자격을 잃으면 복구할 방법도 없습니다. 현재 서비스에는 로그아웃이나 별도 복구 수단이 없어 추가 복잡도에 비해 얻는 것이 적습니다. |
| **400일** | 브라우저가 허용하는 범위에서 PRD 요구에 가장 가깝습니다. 별도의 갱신 로직이 필요하지 않습니다. | 400일이 지나면 자격을 잃습니다. 토큰이 유출되면 그 기간 동안 사용할 수 있습니다. |
| 더 긴 값 | 설정 자체는 가능합니다. | Chrome 계열이 400일로 제한하므로 실제 유지 기간은 늘어나지 않습니다. |

갱신 API는 넣지 않았습니다. 로그아웃도 복구 수단도 없는 구조에서 갱신 기능을 추가해도 안전성이 크게 높아지지 않고, 프론트와 백엔드 양쪽에 관리 코드만 추가됩니다.

현재는 토큰을 명시적으로 갱신하거나 재발급하는 기능도 없습니다. 이후 필요해지면 참여자에 발급 시각을 두고 재발급 API를 추가하는 방식이 자연스럽지만 MVP 범위에서는 제외합니다.

`PARTICIPANT_TOKEN_MAX_AGE`는 400일보다 늘려도 브라우저에서 잘리고, 줄이면 `AC-TOKEN-RESTART` 요구와 멀어집니다.

## 5. 인증 처리 위치: Spring Security가 아니라 ArgumentResolver [확정됨]

`participant/`에 `HandlerMethodArgumentResolver` 하나를 두고, 참여자 자격이 필요한 컨트롤러는 메서드 파라미터로 `Participant`를 받습니다.

Resolver는 다음 처리를 한 곳에서 담당합니다.

- 방 조회. 없으면 `ROOM_NOT_FOUND`
- 쿠키에서 토큰 조회
- 토큰 해시
- 참여자 조회
- 참여자의 방 소속 확인

이 검증은 한 곳에 있어야 빠뜨리기 어렵습니다. 컨트롤러마다 직접 작성하면 하나의 API에서만 검사가 빠져도 방 격리가 깨질 수 있습니다.

필수 자격은 `Participant`, 선택 자격은 `Optional<Participant>`로 받습니다. 메서드 시그니처만 봐도 해당 API가 참여자 자격을 필수로 요구하는지 알 수 있게 합니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 컨트롤러마다 직접 처리 | 별도 구조가 필요 없습니다. | 같은 검증 코드가 여러 곳에 반복되고, 한 곳에서라도 빠뜨리면 방 격리가 깨집니다. 엔드포인트마다 같은 인증 테스트도 반복해야 합니다. |
| Spring Security | 인증·인가를 처리하는 Spring의 표준 구조입니다. 이후 관리자 기능이나 회원 로그인이 생기면 확장하기 좋습니다. 보안 헤더 같은 부가 기능도 함께 사용할 수 있습니다. | 현재 서비스에는 사용자 역할이나 권한 체계, 로그인 흐름이 없습니다. 권한 판정도 "이 참여자가 이 방에 속해 있는가" 하나입니다. SecurityContext와 필터 체인을 넣어도 방 소속 검사는 결국 직접 구현해야 합니다. |
| 서블릿 필터 / 인터셉터 | 컨트롤러에 도달하기 전에 공통으로 처리할 수 있습니다. | 경로에서 방 코드를 꺼내고 참여자를 request attribute에 넣은 뒤 컨트롤러에서 다시 꺼내야 합니다. 필수·선택 여부도 별도의 경로 규칙으로 관리해야 합니다. |
| **`HandlerMethodArgumentResolver`** | 컨트롤러 파라미터로 `Participant`를 선언하면 Resolver가 찾아서 넣어줍니다. 필수는 `Participant`, 선택은 `Optional<Participant>`로 표현할 수 있어 시그니처 자체가 규칙이 됩니다. | Resolver는 서비스 트랜잭션 밖에서 동작합니다. 잠금이 필요한 경우 서비스에서 참여자를 다시 조회해야 합니다. Spring MVC에 묶이는 방식입니다. |

Spring Security는 사용하지 않습니다. 현재 서비스에서 필요한 인증 구조보다 설정과 개념이 더 커지고, 핵심인 방 소속 검사는 별도로 작성해야 합니다. 이후 관리자 화면이나 회원 기반 인증이 실제로 생기면 그때 다시 검토합니다.

한 가지 중요한 제약이 있습니다. Resolver는 서비스 트랜잭션 밖에서 동작합니다. 그래서 답변 제출처럼 참여자 행을 잠가야 하는 기능에서는 Resolver가 넘긴 엔티티를 그대로 사용하면 안 됩니다. 서비스 안에서 참여자 ID로 다시 조회하면서 잠금을 잡아야 합니다.

자격이 없거나 잘못된 요청에 사용할 에러 코드는 아직 규약 표에 없습니다. 현재 제안은 `PARTICIPANT_TOKEN_INVALID` 401 하나로 토큰 없음, 잘못된 토큰, 다른 방의 토큰을 모두 처리하자는 쪽입니다. 다른 방의 자격이라는 정보를 따로 주면 방 존재 여부를 불필요하게 노출할 수 있습니다.

## 6. 프론트와 백엔드 연결: 직접 호출이 아니라 Next rewrite 프록시 [구현됨]

브라우저는 항상 같은 오리진의 `/api`만 호출하고, Next의 `rewrites()`가 해당 요청을 백엔드로 전달합니다.

이 구조는 2번에서 선택한 `SameSite=Lax` 쿠키와 연결되어 있습니다. 브라우저 입장에서 프론트와 API가 같은 사이트로 보이도록 유지해야 쿠키 인증을 단순하게 가져갈 수 있고, 현재 구조에서는 Next rewrite가 가장 적은 코드로 이를 해결합니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 브라우저가 백엔드를 직접 호출 + CORS | 중간 프록시가 없어 요청 구조가 단순합니다. 프론트와 백엔드를 완전히 분리해서 배포할 수 있습니다. | 배포 시 프론트와 백엔드의 사이트가 달라지면 `SameSite=Lax` 쿠키가 API 요청에 전달되지 않을 수 있습니다. 이를 위해 `SameSite=None`으로 바꾸면 CSRF 정책도 다시 설계해야 합니다. 로컬에서는 포트만 달라 문제가 드러나지 않을 수 있습니다. |
| 백엔드가 프론트 정적 빌드를 함께 서빙 | 브라우저 기준 오리진이 하나이고 별도 프록시도 없습니다. | Next의 서버 기능을 사용할 수 없고 프론트 배포가 백엔드 배포와 묶입니다. |
| Next Route Handler로 요청마다 중계(BFF) | 런타임에 환경 변수를 읽을 수 있고, 요청이나 응답을 중간에서 가공할 수 있습니다. | 모든 API에 중계 코드가 필요합니다. 현재는 중간에서 가공해야 할 내용이 없습니다. |
| **Next rewrite로 `/api`를 백엔드에 전달** | 브라우저 기준 오리진을 하나로 유지할 수 있고 CORS 설정이 필요 없습니다. 설정 몇 줄이면 되고 별도 중계 코드도 없습니다. | `BACKEND_ORIGIN`이 빌드 시점에 정해집니다. 서버 컴포넌트에서 직접 호출할 경우 rewrite를 사용할 수 없습니다. |

Route Handler는 런타임에 설정을 바꿀 수 있다는 장점이 있지만, 현재는 같은 이미지를 여러 환경에 그대로 배포해야 한다는 요구가 없습니다. 지금 단계에서는 rewrite로 충분합니다.

쿠키의 `Path`는 요청 경로가 그대로 전달되므로 프록시를 거쳐도 그대로 동작합니다.

현재 구조에서는 배포 대상마다 프론트를 다시 빌드해야 합니다. 이후 동일한 프론트 이미지를 여러 환경에 배포해야 한다면 Route Handler나 middleware를 다시 검토합니다.

데이터를 읽는 화면은 모두 클라이언트 컴포넌트로 둡니다. 서버 컴포넌트에서 백엔드를 직접 호출하면 절대 URL이 필요하고, 현재 rewrite 구조의 장점이 줄어듭니다.

근거: `docs/architecture.md` "프론트엔드 ↔ 백엔드 연결".

## 7. 방 상태를 저장하지 않고 계산함 [구현됨]

방 상태를 별도 컬럼으로 저장하지 않습니다.

방장의 `submitted_at IS NOT NULL`이면 방 상태는 `OPEN`, 참여자의 `submitted_at IS NOT NULL`이면 해당 참여자의 상태는 `SUBMITTED`로 계산합니다. 이 계산은 `RoomStatus.of(Participant)`에서 처리합니다.

같은 사실을 여러 컬럼에 중복해서 저장하지 않으면 서로 값이 어긋날 가능성도 없어집니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| `room.status`, `participant.answer_status` 컬럼 | 현재 상태를 바로 읽을 수 있습니다. 조회 SQL도 단순하고 상태 컬럼에 인덱스를 걸 수도 있습니다. | 방장이 답변을 제출할 때 answer 12행, `participant.submitted_at`, `participant.answer_status`, `room.status`를 모두 맞춰야 합니다. 일부만 반영되면 서로 다른 상태를 나타낼 수 있습니다. `room.status`는 다른 테이블이라 CHECK 제약으로 함께 묶기도 어렵습니다. |
| 상태 전이 이력 테이블 | 상태가 언제 어떻게 변했는지 이력을 남길 수 있습니다. | 현재 도메인은 상태와 전이가 매우 단순합니다. 현재 상태를 알기 위해 마지막 이벤트를 다시 조회해야 하고 구조도 커집니다. |
| **`submitted_at` 하나에서 파생** | 같은 사실을 한 곳에만 저장하므로 서로 어긋날 수 없습니다. 제출 트랜잭션에서 갱신할 컬럼도 줄어듭니다. | 방 상태를 알기 위해 방장 참여자를 함께 읽어야 합니다. 상태 기준 검색이 필요하면 조인이 필요합니다. `RoomStatus.of()`에 올바른 참여자를 넘겨야 하는 책임도 호출자에게 있습니다. |

상태 컬럼을 두는 방식은 조회가 단순하고 상태 검색이 쉽다는 장점이 있습니다. 하지만 이 서비스에는 방 목록을 상태로 검색하는 기능이 없고, 항상 특정 방 하나의 상태만 확인합니다.

반대로 상태 값이 서로 어긋나는 문제는 실제로 발생할 수 있습니다. 예전 설계에서는 두 상태 컬럼을 CHECK 제약으로 맞추려 했는데, 두 컬럼을 계속 맞춰야 한다는 것 자체가 같은 사실을 중복 저장하고 있다는 신호였습니다.

PRD 7장에서도 방 상태를 생성자의 제출 여부에서 파생되는 값으로 정의합니다.

조회 시 방장 참여자를 한 번 더 읽어야 하지만 `room_id` 인덱스를 사용하고, 방마다 참여자 수가 많지 않아 현재 규모에서는 문제가 되지 않습니다.

`RoomStatus.of()`는 넘겨받은 참여자가 실제 방장인지 확인하지 않습니다. 반드시 방장 참여자를 넘겨야 하며, 게스트를 넘기면 오류 없이 잘못된 상태가 계산됩니다.

근거: `docs/database.md` "상태를 컬럼으로 두지 않습니다".

## 8. 방장은 방의 속성이 아니라 참여자의 속성 [구현됨]

방장 여부는 `room`이 아니라 `participant`가 가집니다.

```text
participant.is_host
```

방장 여부와 `room_id`가 같은 참여자 행에 함께 있으므로 "이 방장이 정말 이 방의 참여자인가"를 별도의 참조로 맞출 필요가 없습니다. 방 생성 과정도 이전 구조보다 단순해집니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| `room.host_participant_id` | 방을 조회하면 방장을 바로 알 수 있고, 방마다 방장 하나라는 구조가 컬럼으로 드러납니다. | 참여자보다 방을 먼저 만들어야 해서 생성 중에는 NULL이 필요합니다. `room → participant → room` 순환 참조가 생기고, 방장이 해당 방 참여자라는 것을 DB에서 보장하려면 복합 FK도 필요합니다. 방 생성 과정도 방 → 방장 → 질문 → 방 갱신의 4단계가 됩니다. |
| 별도 `room_host(room_id UNIQUE, participant_id)` 테이블 | NULL과 순환 참조 없이 방장 한 명을 UNIQUE로 보장할 수 있습니다. | 방장 한 명을 표현하기 위해 테이블이 하나 추가되고, 방장을 조회할 때도 조인이 필요합니다. |
| 첫 참여자(id 최소)를 방장으로 간주 | 별도의 컬럼이 필요 없습니다. | 규칙이 스키마에 드러나지 않습니다. 매번 `MIN(id)`를 구해야 하고, 참여자 삭제 기능이 생기면 규칙도 쉽게 깨집니다. |
| **`participant.is_host`** | `room_id`와 방장 여부가 같은 행에 있어 서로 다른 방을 가리킬 수 없습니다. 순환 참조가 없어지고 방 생성 과정도 단순해집니다. | "방마다 방장은 정확히 한 명"이라는 규칙을 DB가 직접 강제하지 않습니다. 방장을 찾기 위해 참여자 조회가 필요합니다. |

기존 `room.host_participant_id` 구조에서는 순환 참조 때문에 테이블 생성 순서도 단순하게 잡히지 않았고, `ALTER TABLE`이 추가로 필요했습니다.

`participant.is_host`로 바꾸면서 이 순환을 없앴고 방 생성도 4단계에서 3단계로 줄었습니다.

"방마다 방장 한 명"이라는 규칙은 DB 제약으로 강제하지 않습니다. 11번에서 정한 기준에 따라 `is_host = TRUE`를 만드는 진입점이 하나이기 때문에 앱에서 보장합니다.

`UNIQUE ((CASE WHEN is_host THEN room_id END))` 형태로 DB에서 강제할 수 있다는 점도 확인했지만 사용하지 않기로 결정했습니다.

`is_host = TRUE`를 만드는 코드는 `Participant.host()` 하나여야 합니다. 초대 링크로 들어오는 참여자는 반드시 `Participant.guest()`를 통해 생성합니다. `new Participant(..., true)`처럼 우회할 수 있는 생성 경로가 생기면 이 결정의 전제가 깨집니다.

## 9. 방의 질문은 복사가 아니라 참조. 질문은 불변 [구현됨]

방에 배정된 질문은 문구를 복사해서 저장하지 않고 `room_question(room_id, question_id)`로 원본 질문을 참조합니다.

대신 `question`의 `category`, `content`, `option_a`, `option_b`는 한 번 등록한 뒤 수정하지 않습니다.

원본 질문이 바뀌지 않는다는 전제가 있으면 방에서는 질문 ID만 보관해도 생성 시점의 질문이 그대로 유지됩니다. 질문 문구도 한 곳에서만 관리할 수 있습니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 값 복사 (`room_question`에 문구·선택지 저장) | 원본 질문을 자유롭게 수정할 수 있고 방 질문을 조회할 때 원본 테이블과 조인하지 않아도 됩니다. | 복사된 값이 기준이므로 이후 원본과 조인하면 안 되는데, 이 규칙을 DB로 막을 수 없습니다. 실수로 원본과 조인하면 기존 방에도 수정된 문구가 보일 수 있습니다. 같은 질문 문구가 방마다 반복 저장됩니다. |
| 참조 + 질문 버전 (`question_version`) | 질문을 수정하면서도 방은 생성 당시 버전을 그대로 참조할 수 있고 수정 이력도 남길 수 있습니다. | 테이블과 조인이 추가되고, 어떤 버전을 활성 상태로 둘지도 관리해야 합니다. 질문 수정 빈도가 낮은 현재 서비스에는 구조가 커집니다. |
| **참조 + 질문 불변** | 문구를 한 곳에서만 관리할 수 있고 원본을 조인해도 과거 방의 질문이 바뀌지 않습니다. 수정이 필요하면 새 질문 행을 추가하고 기존 질문을 비활성화하면 됩니다. | DB가 질문 불변을 직접 강제하지 않습니다. 운영자가 기존 질문을 UPDATE하면 진행 중인 방의 질문도 바뀝니다. |

값 복사 방식과 질문 불변 방식 모두 사람이 지켜야 하는 규칙이 하나씩 있습니다.

값 복사 방식에서는 "기존 방 질문을 읽을 때 원본 질문과 다시 조인하지 않는다"는 규칙을 모든 코드 작성자가 지켜야 합니다. 반면 질문 불변 방식에서는 "기존 질문을 UPDATE하지 않는다"는 규칙을 질문 데이터를 관리하는 곳에서 지키면 됩니다.

질문 수정 이력이 중요한 도메인이라면 버전 테이블이 더 적합하지만, 현재는 질문을 새 행으로 추가하고 기존 행을 `active = FALSE`로 내리는 것으로 충분합니다.

트리거나 컬럼 단위 GRANT를 이용해 불변을 DB에서 강제할 수도 있지만, 현재 규모에서는 관리 부담이 더 크다고 판단해 사용하지 않습니다.

`UNIQUE (category, content)`는 비활성 질문도 포함합니다. 그래서 기존 질문의 선택지만 수정한 새 질문을 등록하거나 비활성화한 문구를 다시 등록하는 경우 문제가 될 수 있습니다. 이 부분은 질문 Pool 운영 방식을 정할 때 함께 다룹니다.

근거: `docs/database.md` "질문은 불변입니다".

## 10. 문항 순서는 별도 컬럼이 아니라 id 오름차순 [구현됨]

질문 순서를 위한 별도 컬럼을 두지 않습니다.

방을 만들 때 선택한 12개 질문을 섞은 순서대로 `room_question`에 INSERT하고, 조회할 때 `ORDER BY rq.id`로 같은 순서를 다시 읽습니다.

`room_question.id`가 `AUTO_INCREMENT`이기 때문에 삽입 순서를 이미 가지고 있습니다. 별도의 순서 컬럼을 추가하면 같은 정보를 두 번 저장하게 됩니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| `room_question.display_order` 컬럼 | 질문 순서가 스키마에 명확히 드러납니다. `UNIQUE (room_id, display_order)`로 중복 순서도 막을 수 있고 화면의 "3/12" 같은 값과 바로 연결할 수 있습니다. | 삽입 순서와 같은 정보를 별도로 한 번 더 저장합니다. 두 값이 어긋날 가능성이 생깁니다. 이전 설계에서는 카테고리별 순서를 고정해 질문이 카테고리 단위로 묶이는 문제도 있었습니다. |
| `room`에 순서 배열을 JSON으로 저장 | 질문 순서가 한 값에 모입니다. | `room_question` 행과 JSON 배열이 서로 어긋날 수 있고 FK로 연결할 수도 없습니다. SQL에서 질문을 조인해 읽기도 어렵습니다. |
| **id 오름차순** | 삽입 순서를 그대로 사용할 수 있어 추가 컬럼이 필요 없습니다. 방 생성 시 섞은 순서가 그대로 질문 순서가 됩니다. | `id`가 식별자와 순서 두 역할을 합니다. 조회에서 `ORDER BY`를 빠뜨려도 오류가 발생하지 않아 순서가 깨질 수 있습니다. |

`display_order`를 사용하면 순서가 명시적이라는 장점이 있습니다. 하지만 이 서비스에서는 질문 순서를 방 생성 시 한 번 정한 뒤 다시 변경하지 않습니다. 별도의 순서 변경 기능도 없습니다.

카테고리 단위로 질문을 묶지 않고 완전히 무작위로 섞는 것은 별도로 결정한 사항입니다. 카테고리별로 묶여 나오면 답변하는 사람이 질문의 의도를 지나치게 의식할 수 있기 때문입니다.

조회하는 쪽에서는 반드시 `ORDER BY rq.id`를 사용해야 합니다. 이를 빠뜨리기 어렵도록 리포지토리 메서드 이름에도 `OrderByIdAsc`를 넣습니다.

프론트가 기존에 사용하던 `displayOrder` 필드를 응답에서 완전히 제거할지, 조회 결과의 인덱스로 만들어 전달할지는 아직 결정 대기입니다.

## 11. DB 제약과 앱 검증의 경계 [구현됨]

DB 제약과 애플리케이션 검증을 나누는 기준을 하나로 정합니다.

**두 요청 사이에 다른 요청이 끼어들 수 있는 규칙은 DB에서 보장하고, 코드의 한 진입점에서 확실하게 보장할 수 있는 규칙은 애플리케이션에서 처리합니다.**

DB 제약은 애플리케이션만으로 막을 수 없는 동시성 문제를 막는 데 씁니다. 반대로 애플리케이션의 단일 진입점에서 이미 보장되는 규칙까지 모두 DB 제약으로 만들면 스키마와 애플리케이션 양쪽에서 같은 규칙을 관리해야 합니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 가능한 규칙을 모두 DB 제약으로 처리 | 애플리케이션에 버그가 있어도 DB가 최종적으로 잘못된 데이터를 막을 수 있습니다. 동시 요청에도 강합니다. | "질문 정확히 12개", "질문 불변" 같은 규칙은 일반적인 제약만으로 표현하기 어렵고 트리거나 권한 관리가 필요합니다. 스키마 변경 시 앱 검증과 DB 제약을 함께 수정해야 하는 경우도 늘어납니다. |
| 모든 규칙을 앱에서 검증 | 규칙을 코드 한 곳에서 읽을 수 있고 원하는 오류 응답을 만들기 쉽습니다. | 조회 후 INSERT하기 전에 다른 요청이 들어오면 두 요청 모두 검증을 통과할 수 있습니다. 닉네임 중복처럼 동시 요청이 가능한 규칙은 앱 검증만으로 보장할 수 없습니다. |
| **기준에 따라 DB와 앱을 나눔** | 동시성이 필요한 규칙은 DB가 맡고, 단일 진입점에서 보장 가능한 규칙은 코드에 둘 수 있습니다. | 규칙마다 어느 쪽에 둘지 판단이 필요합니다. 앱에 맡긴 규칙은 생성 진입점이 하나라는 전제가 유지되어야 합니다. |

현재 규칙은 다음과 같이 나눕니다.

| 규칙 | 어디서 | 이유 |
|---|---|---|
| 한 방에 같은 닉네임 없음 | DB `UNIQUE (room_id, nickname_key)` | 두 요청이 동시에 중복 확인을 통과한 뒤 각각 INSERT할 수 있습니다. |
| 공유 코드 유일, 토큰 해시 유일 | DB `UNIQUE` | 난수 충돌을 최종적으로 막습니다. 토큰 해시는 조회 인덱스 역할도 합니다. |
| 한 사람이 한 질문에 한 번 | DB `UNIQUE (participant_id, room_question_id)` | 중복 답변이 저장되는 것을 막는 안전망입니다. 멱등성 자체의 구현은 아닙니다. |
| 방마다 방장 한 명 | 앱 | `is_host = TRUE`를 만드는 진입점이 하나입니다. |
| 질문은 정확히 12개 | 앱, 방 생성 트랜잭션 | 일반적인 DB 제약만으로 행 개수를 정확히 12개로 제한하기 어렵습니다. |
| 답변의 참여자와 질문이 같은 방 | 앱, 제출 API | DB로 강제하려면 `answer`에 `room_id`를 추가하고 복합 FK를 구성해야 합니다. 참여자의 방 소속은 생성 이후 바뀌지 않으므로 동시성 문제도 없습니다. |
| 질문 불변 | 앱과 운영 규칙 | 9번 결정에 따릅니다. |

앱에서 보장하기로 한 규칙은 진입점이 둘 이상으로 늘어나는 순간 다시 검토해야 합니다.

또한 DB 제약이 선언되어 있다고 해서 모든 입력에서 의도대로 동작한다고 볼 수는 없습니다. 이 저장소에서 발견한 문제도 대부분 제약이 있었지만 후행 공백, 대소문자, NULL, 정규화 결과 같은 특정 값에서 예상과 다르게 통과하는 경우였습니다.

새 제약을 추가하면 정상 입력만 확인하지 않고, 제약을 우회할 수 있는 값도 직접 넣어 확인합니다.

근거: `docs/database.md` "DB가 강제하지 않는 것", "제약이 무력화되던 곳".

## 12. 닉네임: 표시값과 판정 키를 나누고 정규화는 앱이 함 [구현됨]

닉네임은 두 컬럼으로 나눕니다.

- `nickname`: 화면에 보여줄 값
- `nickname_key`: 중복 여부를 판단할 값

닉네임 정규화는 모두 애플리케이션에서 처리합니다.

PRD의 닉네임 비교 규칙은 다음과 같습니다.

- NFC 정규화
- 공백 제거
- 대소문자 구분 없음
- accent는 구분

따라서 `지 은`과 `지은`, `MinSu`와 `minsu`는 같은 닉네임으로 봅니다. 반면 `cafe`와 `café`는 다른 닉네임입니다.

MySQL collation 하나만으로 이 네 조건을 모두 만족시키기 어렵습니다. 결국 일부 정규화는 애플리케이션에서 해야 하고, 일부는 DB에 맡기면 하나의 비교 규칙이 두 곳으로 나뉩니다. 그래서 정규화는 모두 애플리케이션에서 처리하고 DB는 만들어진 키를 그대로 비교하도록 했습니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 컬럼 하나 + 기본 collation (`utf8mb4_0900_ai_ci`) | 컬럼이 하나이고 DB가 대소문자 차이를 알아서 무시합니다. | accent도 무시하기 때문에 `cafe`와 `café`를 같은 값으로 봅니다. NFC 정규화나 공백 제거도 처리하지 못합니다. |
| 컬럼 하나 + 대소문자만 무시하는 collation + 앱 정규화 일부 | 컬럼을 하나로 유지할 수 있습니다. | 정규화 규칙이 앱과 DB에 나뉩니다. 표시값 자체를 정규화해서 저장하면 사용자가 입력한 원래 형태도 잃습니다. |
| 함수 인덱스 (`UNIQUE (room_id, LOWER(nickname))`) | 별도 키 컬럼 없이 UNIQUE를 걸 수 있습니다. | NFC 정규화를 일반적인 SQL 함수로 처리하기 어렵습니다. 공백 제거까지 포함하면 인덱스 식도 복잡해지고, 애플리케이션의 사전 비교 로직과 DB 인덱스 표현식을 같이 유지해야 합니다. |
| **`nickname` + `nickname_key`, 정규화는 앱에서 처리** | 정규화 규칙이 애플리케이션 한 곳에 모입니다. 표시값은 그대로 유지하고 키만 중복 판단에 사용합니다. | `nickname_key`가 `nickname`에서 계산되는 파생 값이라 3NF를 위반합니다. 정규화 코드가 잘못되면 DB는 이를 다시 보정하지 않습니다. |

`Nickname.of()`에서 표시값과 판정 키를 같이 만듭니다.

표시값은 trim과 연속 공백 한 칸 정리 정도만 하고, 판정 키에는 추가로 NFC 정규화, 모든 공백 제거, `toLowerCase(Locale.ROOT)`를 적용합니다.

`nickname_key`는 `utf8mb4_0900_as_cs`로 두고 DB에서는 만들어진 문자열을 그대로 비교합니다. 중복은 `UNIQUE (room_id, nickname_key)`로 막습니다.

소문자 변환에는 반드시 `Locale.ROOT`를 사용합니다. 기본 로케일을 사용하면 터키어 환경에서 `I`가 `ı`로 변환되는 것처럼 실행 환경에 따라 정규화 결과가 달라질 수 있습니다.

정규화 과정에서 문자 수가 늘어날 수 있으므로 `nickname_key` 길이는 최대 확장을 고려해 48로 둡니다.

서버는 프론트에서 수행한 정규화를 신뢰하지 않고 동일한 규칙을 다시 적용합니다.

짝이 맞지 않는 대리 문자(`\p{Cs}`)도 입력 단계에서 거절합니다. JDBC가 이런 값을 오류 없이 `?`로 바꿔 저장하는 것을 실제로 확인한 뒤 추가한 규칙입니다.

근거: `docs/database.md` "nickname과 nickname_key를 나눔", `Nickname.java` 주석.

## 13. 공유 코드: 128비트 난수, 충돌 재시도 없음 [구현됨]

공유 코드는 `SecureRandom`으로 만든 16바이트 난수를 패딩 없는 Base64URL로 인코딩한 22자 문자열을 사용합니다.

DB에서는 `utf8mb4_0900_bin`으로 비교하고, 공유 코드 충돌이 발생했을 때 애플리케이션에서 별도 재시도를 하지 않습니다.

공유 코드를 알고 있으면 해당 방에 접근할 수 있기 때문에 쉽게 추측할 수 없어야 합니다. PRD 17장에서도 최소 128비트의 난수를 요구하므로 짧은 코드나 순차 ID 기반 방식은 사용하지 않습니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 순차 ID 인코딩(Hashids 등) | 코드가 짧고 충돌이 없습니다. | 순차 값에 기반하기 때문에 다른 방 코드를 추측할 수 있습니다. 인코딩은 난독화이지 비밀값 생성이 아닙니다. PRD 17장 요구에도 맞지 않습니다. |
| 짧은 난수(6~8자) + 충돌 시 재시도 | URL이 짧아 공유하기 편합니다. | 엔트로피가 충분하지 않고 실제 충돌 가능성도 커집니다. 충돌 재시도 로직이 필요합니다. |
| UUID v4 | 표준 포맷이고 라이브러리 지원도 좋습니다. | 문자열이 36자로 길고 하이픈이 포함됩니다. 실제 랜덤 비트도 122비트입니다. |
| **16바이트 `SecureRandom` → Base64URL 22자** | 128비트 난수를 그대로 사용할 수 있고 URL에 바로 넣을 수 있습니다. UUID보다 짧습니다. | 22자라 사람이 직접 입력하기에는 길고, 대소문자를 구분하므로 DB collation도 이를 맞춰야 합니다. |

UUID v4와 비교하면 Base64URL 방식이 더 짧으면서 128비트를 그대로 사용할 수 있습니다.

충돌 시 재시도를 넣지 않은 것은 충돌 확률이 낮아서만은 아닙니다. UNIQUE 위반으로 트랜잭션이 실패한 상태에서 같은 트랜잭션 안에서 다시 INSERT하는 잘못된 재시도 구조를 만들기 쉽습니다.

현재 엔트로피에서는 충돌을 정상적인 비즈니스 흐름으로 다룰 필요가 없다고 판단했습니다. 충돌하면 서버 오류로 처리하고 사용자가 다시 요청합니다.

초대 링크는 프론트에서 `/r/{code}` 형태로 최대한 짧게 사용합니다.

`ascii_bin`이 아니라 `utf8mb4_0900_bin`을 사용하는 이유와 PAD SPACE 관련 내용은 `docs/database.md`에 따로 정리합니다.

공유 코드는 로그에 남기지 않습니다. 방에 접근할 수 있는 값이므로 자격 정보에 준해서 다룹니다.

## 14. 답변 제출의 멱등성: UNIQUE가 아니라 행 잠금 [확정됨]

답변 제출 트랜잭션은 참여자 행을 `SELECT ... FOR UPDATE`로 잠그는 것부터 시작합니다.

잠금을 얻은 뒤 `submitted_at`을 확인합니다.

이미 제출한 참여자라면 기존 답변과 새 요청을 집합으로 비교합니다.

- 같은 답변이면 기존 제출과 같은 성공으로 처리
- 다른 답변이면 409 반환

아직 제출하지 않았다면 답변 12행을 저장하고 `submitted_at`을 채웁니다.

PRD 9장과 API 규약에서 요구하는 동작은 다음 네 가지입니다.

- 같은 12개 답변을 다시 보내면 배열 순서가 달라도 성공
- 기존과 다른 답변을 다시 보내면 409
- 같은 제출 요청 두 개가 동시에 들어오면 둘 다 성공하고 데이터는 한 번만 저장
- 다른 제출 요청 두 개가 동시에 들어오면 하나만 성공하고 답변이 섞이지 않음

UNIQUE 제약만으로는 "같은 요청이면 성공으로 본다"는 판단을 할 수 없습니다. 판정을 애플리케이션에서 해야 한다면 판정과 저장 사이에 다른 요청이 끼어들지 못하게 해야 하고, 이를 위해 참여자 행을 잠급니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| `UNIQUE (participant_id, room_question_id)`에만 의존 | 별도 동시성 제어 코드가 필요 없습니다. | UNIQUE는 두 제출의 내용이 같은지 알 수 없습니다. 두 번째 요청은 중복 INSERT에서 제약 위반으로 실패하고, 동일 제출을 성공으로 처리할 수 없습니다. |
| INSERT 전에 `submitted_at` 확인, 잠금 없음 | 순차 요청에서는 요구사항대로 동작합니다. | 확인과 INSERT 사이에 다른 요청이 들어오면 둘 다 미제출로 판단할 수 있습니다. 뒤 요청은 UNIQUE 위반으로 실패할 수 있습니다. |
| 낙관적 잠금 (`@Version`) | DB 행을 미리 잠그지 않습니다. | 충돌 시 예외가 발생하므로 재시도 처리가 필요합니다. 재시도 과정에서 다시 같은 답변인지 비교해야 해서 흐름이 더 복잡해집니다. |
| 클라이언트 멱등 키 (`Idempotency-Key`) | 일반적인 멱등 요청 구조로 만들 수 있습니다. | 키를 저장할 곳이 별도로 필요하고 프론트에서 키 생성과 보관도 해야 합니다. 현재 요구에서는 "같은 답변 내용" 자체가 멱등 판단 기준입니다. |
| **참여자 행 `SELECT ... FOR UPDATE`** | 같은 참여자의 제출만 직렬화됩니다. 뒤 요청은 앞 요청이 끝난 뒤 결과를 보고 같은 제출인지 다른 제출인지 정확히 판단할 수 있습니다. | 트랜잭션 안에서 다시 조회해야 합니다. 같은 참여자의 동시 제출 시 잠금 대기가 발생합니다. |

`UNIQUE (participant_id, room_question_id)`는 그대로 유지합니다. 다만 이 제약은 멱등성을 구현하는 수단이 아니라, 잠금이나 애플리케이션 로직에 문제가 생겼을 때 답변이 중복 저장되는 것을 막는 마지막 안전망입니다.

5번의 ArgumentResolver가 넘긴 `Participant` 객체를 그대로 사용하면 행 잠금이 적용되지 않습니다. 서비스 트랜잭션 안에서 ID로 다시 조회하면서 `FOR UPDATE`를 사용해야 합니다.

`submitted_at`은 애플리케이션의 `LocalDateTime.now()`가 아니라 DB의 `NOW(6)`으로 채웁니다. `created_at`과 같은 기준의 시간을 사용하기 위해서입니다.

동시 요청에 대해서는 최소 두 가지 테스트를 유지합니다.

- 같은 답변 두 요청 동시 제출
- 다른 답변 두 요청 동시 제출

이 테스트들이 이 결정의 회귀 방지 역할을 합니다.

근거: `docs/domain.md` "멱등성은 UNIQUE로 달성되지 않습니다".

## 15. 케미 점수는 저장하지 않고 조회할 때 계산 [확정됨]

케미 점수는 DB에 저장하지 않습니다.

결과 API에서 방의 완료 참여자와 답변을 한 번 조회한 뒤 메모리에서 점수를 계산합니다. `result/` 패키지는 DB 접근 없이 계산 로직만 가지도록 합니다.

PRD 성능 기준선인 완료자 100명을 기준으로 보면 답변은 1,200행입니다. 참여자 Pair는 4,950개이고 질문별 비교를 포함해도 비교 횟수는 약 6만 번 정도입니다.

현재 규모에서는 매 조회마다 계산해도 충분히 작고, 점수를 저장하거나 캐시하면서 생기는 정합성 관리가 더 복잡합니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| Pair 점수 테이블에 저장하고 제출 때 갱신 | 결과 조회가 단순해지고 순위도 SQL로 바로 구할 수 있습니다. | 한 명이 제출할 때 기존 완료자 수만큼 점수 행을 추가해야 합니다. 답변과 점수가 서로 어긋날 가능성이 생기고 점수 규칙이 바뀌면 기존 데이터를 모두 다시 계산해야 합니다. |
| 조회 결과 캐시 | 반복 조회가 빠릅니다. | 새로운 제출이 생길 때마다 캐시를 무효화해야 합니다. 현재 계산 규모에서는 캐시 필요성이 크지 않습니다. |
| DB에서 SQL로 계산 (`answer` self-join) | 데이터를 애플리케이션으로 모두 가져오지 않아도 됩니다. | competition ranking, 닉네임 기반 안정 정렬, 반전 조합, 공동 리더 같은 결과 규칙을 SQL로 표현하고 테스트하기가 복잡합니다. |
| **조회할 때 앱에서 계산** | 저장되는 파생 데이터가 없어 답변과 점수가 어긋날 일이 없습니다. 계산 규칙을 Java 코드 한 곳에 둘 수 있고 DB 없이 단위 테스트할 수 있습니다. | 결과 조회마다 답변을 다시 읽고 계산합니다. 방 규모가 매우 커지면 계산량이 늘어납니다. |

현재 점수 계산량은 p95 500ms 성능 기준보다 충분히 작을 것으로 예상합니다. 따라서 저장이나 캐시를 추가하지 않습니다.

결과 정렬 규칙도 한 곳에서만 처리합니다. "정규화된 닉네임 오름차순"은 Java에서 `nickname_key`의 코드포인트 순으로 처리합니다. MySQL의 `as_cs` collation 정렬 결과와 Java 정렬이 반드시 같다고 볼 수 없기 때문에 DB와 앱 양쪽에서 순서를 만들지 않습니다.

결과 응답에는 모든 Pair를 담지 않습니다. PRD 11장과 `NFR-PERF-04`에 따라 다음 상한을 둡니다.

- TOP 3
- 카테고리 4개
- 반전 1개
- 내 Pair 10개

완료자 100명을 넘는 방은 PRD 17장 기준 성능 보장 범위 밖입니다.

## 16. 에러 응답: code가 계약이고 상태와 1:1 [구현됨]

모든 API 실패 응답은 다음 형식으로 통일합니다.

```json
{
  "code": "...",
  "message": "..."
}
```

프론트가 의존하는 계약은 `message`가 아니라 `code`입니다. 각 `code`에는 하나의 HTTP 상태를 연결합니다.

응답 형식 자체는 위키 API 규약에서 이미 정해져 있었습니다. 이 항목에서 추가로 결정한 부분은 두 가지입니다.

- `ApiException.reason`은 응답에 넣지 않고 로그에만 남깁니다.
- `GlobalExceptionHandler`는 `ResponseEntityExceptionHandler`를 상속합니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| HTTP 상태만 사용 | 별도의 에러 바디가 필요 없습니다. | 같은 409라도 닉네임 중복, 기존 제출과 다른 재제출, 방 상태 문제 등을 구분할 수 없습니다. |
| 상태 + 자유로운 message | 사람이 읽기 쉽습니다. | 프론트가 message 문자열을 기준으로 분기하게 될 수 있습니다. 문구를 바꾸는 것이 API 계약 변경으로 이어질 수 있습니다. |
| RFC 9457 `ProblemDetail` | 표준 형식이고 Spring에서도 기본 지원합니다. | 현재 프론트는 `code` 기반 분기를 요구하고 있고, 별도의 `type` URI 체계를 운영할 필요도 없습니다. 기존 위키 규약과도 다릅니다. |
| **`{code, message}` 고정** | 프론트는 `code`만 보고 분기할 수 있고 `message`는 자유롭게 수정할 수 있습니다. `ApiErrorCode`가 HTTP 상태도 함께 가지고 있어 같은 코드가 다른 상태로 나가는 것을 막을 수 있습니다. | 새로운 실패 상황이 생길 때마다 에러 코드 규약을 추가해야 합니다. `ApiErrorCode`가 HTTP 상태를 알아 도메인 코드와 HTTP 계층 사이의 경계가 완전히 분리되지는 않습니다. |

`reason`을 응답에 넣지 않는 이유는 내부 처리 이유가 사용자 응답에 그대로 노출되는 것을 막기 위해서입니다. 같은 `code`에서도 내부 원인은 다를 수 있으므로 `reason`은 서버 로그에서만 확인합니다.

`ResponseEntityExceptionHandler`를 상속하는 이유는 Spring MVC 자체에서 발생한 예외의 HTTP 상태를 유지하기 위해서입니다.

`@ExceptionHandler(Exception.class)` 하나만 두면 잘못된 URL이나 지원하지 않는 HTTP method 같은 요청까지 모두 500으로 처리될 수 있습니다. 부모 핸들러를 사용하면 Spring이 이미 알고 있는 404, 405 등의 상태는 유지하면서 응답 바디만 `{code, message}` 형식으로 통일할 수 있습니다.

없는 URL은 `NOT_FOUND`, 존재하지 않는 방은 `ROOM_NOT_FOUND`로 구분합니다. 그래야 프론트가 모든 404를 "없는 방" 화면으로 처리하지 않습니다.

현재 구조에는 계층 측면에서 애매한 곳이 하나 있습니다.

`Nickname`, `RoomQuestionFactory` 같은 도메인 코드가 `ApiException`을 던지고, `ApiErrorCode`는 `HttpStatus`를 알고 있습니다. 반면 `docs/architecture.md`에는 Service와 Entity가 HTTP 개념을 다루지 않는다고 적혀 있습니다.

현재는 `ApiErrorCode`를 단순 HTTP 구현 세부가 아니라 API 계약의 오류 코드로 보고 사용하고 있지만, 계층 분리를 더 엄격하게 가져가려면 이후 다시 정리할 수 있는 부분입니다.

415와 406은 위키 API 규약의 표에 코드를 추가했습니다(2026-09-11 사용자 결정). `UNSUPPORTED_MEDIA_TYPE`과 `NOT_ACCEPTABLE`입니다.

그전에는 둘 다 상태만 살리고 `code`는 `VALIDATION_FAILED`로 내려갔습니다. 그 코드는 400으로 선언돼 있어서 415 응답에 400짜리 코드가 실렸습니다. `ApiErrorCode`가 코드마다 상태를 하나씩 들고 있다고 선언해 놓고 핸들러가 그것을 깨고 있었습니다.

413은 코드를 만들지 않았습니다. Spring MVC가 413을 내는 경로는 multipart 요청 하나인데 이 API에는 multipart를 받는 엔드포인트가 없습니다. MockMvc는 multipart 파싱을 흉내만 내서 실제로 413이 나가는지는 확인하지 못했습니다. 필요해지면 위키 표에 코드를 먼저 추가합니다.

`RoomCreationTest.공통_코드는_선언한_HTTP_상태로만_나간다`가 이 규칙을 지킵니다. 응답에서 읽은 `code`로 `ApiErrorCode`를 다시 찾아 그 `status()`와 실제 응답 상태를 비교합니다. 상태와 코드를 각각 기댓값으로 적어 두면 둘 다 틀리게 적었을 때 통과합니다.

근거: `docs/conventions.md` "Exception / API 응답", 위키 API 규약.

## 17. 트랜잭션 경계는 Service, 컨트롤러는 엔티티를 모름 [구현됨]

트랜잭션은 Service에서 시작합니다.

컨트롤러는 엔티티를 직접 받지 않고 서비스가 반환하는 값인 `CreatedRoom` 등을 사용합니다. `open-in-view`는 `false`로 둡니다.

방 생성에서는 방, 방장 참여자, 질문 12개가 하나의 작업으로 저장되어야 합니다. 중간 단계에서 하나라도 실패하면 전체가 롤백되어야 하므로 이 작업 전체를 Service 트랜잭션으로 묶습니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 컨트롤러에 `@Transactional` | 계층이 하나 줄고 코드가 짧아질 수 있습니다. | HTTP 요청과 응답을 다루는 동안 트랜잭션이 계속 열려 있을 수 있습니다. 컨트롤러가 엔티티를 직접 알게 되고, 직렬화 과정에서 지연 로딩이 일어날 가능성도 생깁니다. |
| 리포지토리 호출마다 각각 커밋 | 별도의 서비스 트랜잭션 구성이 필요 없습니다. | 방 저장 후 방장이나 질문 저장이 실패하면 불완전한 방이 DB에 남을 수 있습니다. |
| 도메인 이벤트 + 아웃박스 | 후속 처리를 비동기로 분리하거나 확장하기 좋습니다. | 현재 방 생성의 세 저장은 모두 한 번에 성공해야 하는 작업입니다. 별도의 후속 처리도 없어 지금 단계에서는 구조만 커집니다. |
| **Service에 `@Transactional`, 컨트롤러는 서비스 반환값만 사용, `open-in-view: false`** | 여러 저장을 한 트랜잭션으로 묶을 수 있습니다. 쿼리가 발생하는 위치도 서비스 안으로 제한됩니다. 컨트롤러는 DB 엔티티 구조를 몰라도 됩니다. | 서비스 반환값과 API 응답 DTO가 별도로 존재해 클래스가 늘어납니다. 응답 값이 바뀌면 두 구조를 같이 수정해야 할 수 있습니다. |

이 경계가 실제로 유효했던 사례도 있습니다.

ERD를 다시 설계하면서 방 생성 절차가 4단계에서 3단계로 바뀌었지만 `RoomController`는 수정하지 않았습니다. 컨트롤러가 엔티티 구조를 직접 알지 않습니다.

반대로 제거된 DB 컬럼을 직접 사용하던 엔티티와 서비스는 수정이 필요했습니다.

`open-in-view`를 끄면 컨트롤러의 응답 직렬화 과정에서 지연 로딩으로 추가 쿼리가 발생하는 경로도 막을 수 있습니다. 필요한 데이터는 서비스 트랜잭션 안에서 모두 조회해야 합니다.

대신 DTO가 두 종류 존재합니다. 예를 들어 `CreatedRoom`에는 `accessToken`이 있지만 `CreateRoomResponse`에는 없습니다. 토큰이 응답 바디가 아니라 쿠키로 나가기 때문입니다.

## 18. 패키지는 계층별이 아니라 도메인별 [구현됨]

패키지는 다음과 같이 도메인 기준으로 나눕니다.

```text
room/
question/
participant/
answer/
result/
common/
```

각 도메인 패키지 안에서 controller, service, repository 등의 역할을 나눕니다.

`ShareCodeGenerator`는 `room/`, `AccessTokenGenerator`는 `participant/`에 둡니다. 각각 방의 식별자와 참여자의 자격 정보를 만듭니다.

현재 저장소의 실제 작업 단위도 "방 생성", "답변 제출", "결과 조회"처럼 도메인 기능 중심입니다. `CLAUDE.md`에서도 하나의 기능을 볼 때 해당 도메인 디렉터리에서 탐색을 시작하도록 정하고 있습니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 계층별 (`controller/`, `service/`, `repository/`, `entity/`) | Spring 프로젝트에서 흔한 구조라 익숙하고, 계층별 코드를 한 곳에서 볼 수 있습니다. 패키지 가시성을 이용해 일부 계층 규칙을 강제하기도 쉽습니다. | 하나의 기능을 수정할 때 여러 디렉터리를 오가야 합니다. 도메인이 늘어날수록 각 계층 디렉터리도 계속 커집니다. |
| Gradle 멀티모듈 | 모듈 간 의존 방향을 빌드 단계에서 강제할 수 있습니다. 잘못된 순환 의존이 컴파일 오류로 드러납니다. | 현재 규모에서는 빌드 구조와 설정이 크게 늘어납니다. 초기에 경계를 잘못 나누면 다시 옮기는 비용도 큽니다. |
| **도메인별 패키지** | 하나의 기능에 관련된 코드를 가까이 둘 수 있습니다. 도메인이 늘어날 때도 별도 디렉터리로 분리됩니다. | 계층 간 의존 규칙을 패키지 자체로 강제하기는 어렵습니다. 도메인 사이에 순환 의존이 생겨도 Java 컴파일러가 막아주지 않습니다. |

`common/`은 처음부터 공용 코드 후보를 넣는 곳으로 쓰지 않습니다. 실제로 둘 이상의 도메인에서 함께 사용하게 된 코드만 옮깁니다.

현재 `room ↔ participant` 사이에는 순환 의존이 있습니다.

```text
RoomStatus → Participant → Room
```

Java 패키지 구조에서는 허용되며 현재 규모에서는 문제가 되지 않습니다. 다만 두 도메인의 경계가 완전히 분리된 것은 아니라는 의미입니다.

`Participant`를 `Room` 집합체의 일부로 본다면 지금 구조가 맞습니다. 이후 멀티모듈로 분리할 필요가 생기면 이 순환은 그대로 둘 수 없으므로 그 시점에 다시 정리합니다.

## 19. 스키마는 SQL 파일이 소유. Hibernate가 만들지 않음 [구현됨, 마이그레이션 도구는 대기]

DB 스키마는 `database/init/01-schema.sql`이 관리합니다.

Hibernate의 `ddl-auto`는 `none`으로 두고, 현재 개발 단계에서는 스키마를 변경하면 DB 볼륨을 삭제한 뒤 다시 생성합니다.

이 프로젝트의 스키마는 collation, 바이너리 컬럼, 제약 조건 등 DB 설정 자체에 의미가 있습니다. Hibernate가 자동 생성하는 DDL만으로는 이 구조를 그대로 표현하거나 확인하기 어렵습니다.

또한 SQL 파일에 제약마다 왜 필요한지 주석을 남기는 방식을 사용하고 있습니다. 실제로 스키마 관련 결함을 수정하면서 같은 문제가 다시 생기지 않도록 근거를 남기는 데 사용했습니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| Hibernate `ddl-auto: update/create` | 엔티티를 수정하면 스키마를 자동으로 생성하거나 변경해 초기 개발이 빠릅니다. | 컬럼별 collation, `BINARY(32)`, ENUM, `ON DELETE` 동작 같은 세부 설정을 의도대로 관리하기 어렵습니다. `update`는 제거된 컬럼을 자동으로 정리하지 않는 등 실제 스키마가 엔티티와 달라질 수 있습니다. |
| 처음부터 Flyway/Liquibase 사용 | 스키마 변경 이력이 버전별로 남고 운영 데이터가 있는 상태에서도 순차적으로 적용할 수 있습니다. 테스트와 운영에 동일한 마이그레이션을 적용할 수도 있습니다. | 첫 스키마부터 마이그레이션 규칙에 맞춰 관리해야 하고 현재의 단순한 볼륨 재생성 방식보다 관리 규칙이 늘어납니다. |
| **`01-schema.sql`이 스키마 소유, `ddl-auto: none`** | SQL을 직접 관리하므로 collation과 제약을 명확하게 지정할 수 있고 각 제약의 이유도 주석으로 남길 수 있습니다. Testcontainers에서도 같은 SQL을 사용할 수 있습니다. | 엔티티를 바꿔도 DB 스키마가 자동으로 따라오지 않습니다. 둘이 어긋나면 런타임에서 문제가 발생합니다. 운영 데이터가 생기면 볼륨 삭제 방식은 더 이상 사용할 수 없습니다. |

Flyway 도입 여부는 아직 결정하지 않았습니다.

현재는 초기 개발 단계라 DB를 다시 만들어도 되지만, 실제 운영 데이터가 생긴 뒤에는 스키마를 삭제하고 다시 만들 수 없습니다. 운영 데이터가 생기기 전에 마이그레이션 방식을 정해야 합니다.

엔티티와 SQL 스키마가 어긋나는 문제는 실제 MySQL에 붙는 통합 테스트에서 잡습니다. 이 때문에 20번의 Testcontainers 테스트와 이 결정은 서로 연결되어 있습니다.

## 20. 테스트는 인메모리 DB가 아니라 실제 MySQL [구현됨]

통합 테스트에서는 Testcontainers로 MySQL 8.4를 실행합니다.

DB 저장 결과를 확인할 때는 JPA 리포지토리만 사용하지 않고 `JdbcTemplate`으로 실제 컬럼 값을 직접 조회합니다.

통합 테스트에는 `@Transactional`을 붙이지 않습니다.

반대로 `Nickname`, 앞으로의 `result/`처럼 DB가 필요 없는 계산 규칙은 일반 단위 테스트로 분리합니다.

이 저장소에서 지금까지 발견된 DB 관련 문제는 대부분 "제약을 선언했지만 특정 값에서는 예상과 다르게 동작하는 경우"였습니다. 이런 문제를 확인하려면 실제 MySQL의 collation, 문자열 비교, 타입 처리 방식이 필요합니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| H2 인메모리 DB | 빠르고 Docker가 필요 없습니다. CI 구성도 단순합니다. | MySQL의 collation, NO PAD, ENUM, `ON DELETE`, BINARY 비교 등을 동일하게 재현하지 못합니다. `MODE=MySQL`을 사용해도 collation 동작까지 같아지지는 않습니다. |
| 리포지토리 mock | DB 없이 서비스 로직만 빠르게 테스트할 수 있습니다. | 확인하려는 문제가 엔티티와 실제 DB 스키마 사이의 차이인데 mock을 사용하면 그 부분을 확인할 수 없습니다. |
| 공유 개발 DB 사용 | 실제 MySQL 엔진에서 테스트할 수 있습니다. | 테스트 데이터가 서로 섞일 수 있고 병렬 실행이 어렵습니다. 개발자마다 DB 상태가 달라질 수도 있습니다. |
| **Testcontainers + MySQL 8.4** | 운영과 같은 DB 엔진과 같은 스키마 SQL을 사용할 수 있습니다. 테스트마다 독립된 DB를 만들 수 있습니다. | Docker가 필요하고 첫 컨테이너 기동 시간이 있습니다. Spring 컨텍스트 캐시를 제대로 사용하지 않으면 테스트 시간이 크게 늘어날 수 있습니다. |

`JdbcTemplate`으로 실제 컬럼을 직접 읽는 이유도 `ddl-auto: none`과 연결되어 있습니다.

엔티티 매핑이 잘못된 상태에서 다시 같은 엔티티를 통해 조회하면 일부 문제가 가려질 수 있습니다. 실제 컬럼 값을 직접 확인하면 엔티티와 스키마가 어긋난 부분을 더 명확하게 볼 수 있습니다.

통합 테스트에 `@Transactional`을 붙이지 않습니다. 테스트 자체 트랜잭션 안에서 컨트롤러 요청까지 실행되면 실제 커밋이 일어나지 않아 롤백이나 트랜잭션 경계 테스트가 제대로 검증되지 않을 수 있기 때문입니다.

통합 테스트의 애노테이션 조합은 `@IntegrationTest` 하나로 통일합니다. 테스트 클래스마다 조합이 달라지면 Spring이 서로 다른 컨텍스트로 인식해 새로 띄울 수 있고, 컨테이너 기동 비용도 반복될 수 있습니다.

`ChemiLogApplicationTests`를 단순 `@SpringBootTest`로 두는 것도 피합니다. 테스트 환경의 `${DB_PASSWORD}` 같은 설정이 없으면 실제 테스트 목적과 관계없는 설정 오류로 실패할 수 있습니다.

또한 `compileJava` 성공을 테스트 성공으로 보지 않습니다. 의존성 좌표 문제로 테스트 코드가 한 번도 실행되지 않은 상태에서 컴파일만 통과한 적이 있었습니다.

## 21. 시각: DATETIME과 서버 시간대 [대기]

아직 최종 결정하지 않았습니다.

현재 제안은 MySQL 서버 옵션에 다음 값을 주는 쪽입니다.

```text
--default-time-zone=+09:00
```

운영용 MySQL과 Testcontainers 양쪽에 같은 설정을 넣어 DB가 항상 같은 기준의 시간을 사용하도록 합니다.

현재 스키마는 `DATETIME`을 사용합니다. `DATETIME` 자체에는 시간대 정보가 없기 때문에 같은 값이라도 어떤 기준의 시간으로 저장했는지를 애플리케이션과 DB 설정으로 정해야 합니다.

현재 운영 compose에서는 `TZ: Asia/Seoul` 환경 변수를 사용하지만 Testcontainers에는 같은 설정이 없어 UTC로 실행될 수 있습니다.

`created_at`은 DB의 `DEFAULT CURRENT_TIMESTAMP(6)`가 만들고, `submitted_at`도 DB의 `NOW(6)`를 사용합니다. API 규약에서는 응답 시각을 Asia/Seoul 기준으로 정의합니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 현재처럼 OS 환경 변수에 의존 | 별도 변경이 필요 없습니다. | 실행 환경에 따라 DB 시간대가 달라질 수 있습니다. Testcontainers와 운영 환경이 서로 다른 시간으로 동작할 가능성도 있습니다. 관리형 MySQL에서는 서버가 UTC인 경우도 많습니다. |
| **MySQL `--default-time-zone=+09:00`** | OS 설정과 관계없이 MySQL 자체의 시간대를 고정할 수 있습니다. 테스트와 운영에 같은 옵션을 넣으면 같은 조건에서 동작합니다. | `Asia/Seoul` 같은 지역 이름이 아니라 고정 오프셋을 사용합니다. 한국은 현재 서머타임이 없어 실제 동작에는 문제가 없습니다. |
| UTC로 저장하고 응답에서 +09:00 변환 | 서버가 어느 지역에서 실행되더라도 저장 기준이 하나로 고정됩니다. 일반적으로 시간대 처리에 가장 명확한 방식입니다. | 현재 `LocalDateTime`, `NOW(6)`, DB 직접 조회 방식 등 관련 코드를 함께 수정해야 합니다. 개발 중 DB를 직접 볼 때 한국 시간보다 9시간 이전 값이 보입니다. |
| `TIMESTAMP` 타입 사용 | MySQL이 세션 시간대에 따라 값을 변환해줍니다. | 저장과 조회 결과가 세션 시간대 설정에 영향을 받습니다. 타입 변경도 필요하고, 2038년 범위 제한도 고려해야 합니다. |

시각 값을 실제 API 응답에 사용하기 전에 이 결정은 끝내야 합니다.

어느 방식을 선택하더라도 `LocalDateTime.now()`로 `submitted_at`을 채우지 않는 규칙은 유지합니다.

JVM 컨테이너가 UTC이고 MySQL이 +09:00이라면 `LocalDateTime.now()`로 만든 값이 DB 기준 시간보다 9시간 이전으로 저장될 수 있고, DB는 이를 오류로 판단하지 않습니다.

`created_at`과 `submitted_at` 모두 같은 시간 기준을 사용하도록 한 곳, 즉 DB에서 만드는 것이 현재 원칙입니다.

## 22. 방 참여 인원과 만료: 두지 않음 [확정됨]

참여자 수 상한과 방 만료 기능을 두지 않습니다.

스키마에도 만료 시각 컬럼을 추가하지 않습니다.

PRD 7장과 16장에서 현재 범위에서는 두 기능을 제공하지 않기로 했습니다. 실제 요구가 없는 상태에서 미리 컬럼과 정책을 만들지 않고, 필요해지는 시점에 추가합니다.

검토한 선택지입니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 참여자 수 상한 | 결과 계산량과 데이터 크기에 명확한 최대값을 둘 수 있습니다. | 상한 값을 별도로 정해야 하고, 초과 시 사용자에게 보여줄 화면과 에러 처리도 필요합니다. 현재 PRD에서는 상한을 두지 않기로 했습니다. |
| 방 만료 (`expires_at` + 정리 작업) | 오래된 데이터가 계속 쌓이는 것을 막을 수 있습니다. | 만료 기준을 정해야 하고 주기적으로 데이터를 정리하는 작업도 필요합니다. 만료된 링크에 접근했을 때의 화면과 API 동작도 추가로 설계해야 합니다. |
| **둘 다 두지 않음** | 현재 PRD 그대로 구현할 수 있고 추가 스키마나 백그라운드 작업이 필요 없습니다. | 데이터가 기간 제한 없이 계속 쌓입니다. 참여자가 매우 많은 방은 결과 계산량도 계속 증가할 수 있습니다. |

데이터 정리 정책은 실제 서비스 사용량을 확인한 뒤 정합니다.

그전까지 방과 참여자 데이터는 별도의 만료 없이 유지됩니다.

현재 DB 관계에서는 `participant.room_id`가 `RESTRICT`이므로 운영자가 방을 직접 삭제해야 할 경우 참여자를 먼저 삭제하고 방을 나중에 삭제해야 합니다.

참여자가 100명을 넘는 방은 PRD 17장에서 성능 보장 범위 밖으로 정의합니다.

설계 결정이 바뀌더라도 기존 내용을 단순히 삭제하지 않습니다. **기존에 어떤 방식을 사용했고, 무엇으로 바꿨으며, 왜 바꿨는지**를 남깁니다. 7번, 8번, 9번이 그 예입니다.

선택지 표에는 선택한 방식뿐 아니라 검토한 방식의 장점과 단점도 함께 적습니다. 선택하지 않은 방식에도 분명 장점이 있었기 때문에, 그것을 남겨야 이후 같은 대안을 다시 검토할 때 당시의 판단 근거를 확인할 수 있습니다.

구현 세부사항은 코드와 다른 `docs/` 문서에 둡니다. 이 문서에는 설계 결정과 그 판단 근거만 남깁니다.
